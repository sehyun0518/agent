# ADR-0021 — 무엇을 알고 싶은지는 어디서 묻는가

- 상태: 채택
- 날짜: 2026-09-01
- 다루는 축: 요구사항 슬롯, 관측성
- 관련: ADR-0019(관측성 자리) · `packages/boundary-contracts/requirements-spec/SKILL.md`

## 맥락

필수 슬롯 여섯이 이렇게 묻는다.

```text
goal  target  design_ref  scope_in  scope_out  acceptance_criteria
```

`goal`이 "사용자가 무엇을 달성하나"를 묻는데 **그게 달성됐는지 확인하는 방법은 아무도
묻지 않는다.**

`acceptance_criteria`가 있지만 다른 질문이다.

| | 무엇을 묻나 | 언제 답이 나오나 |
|---|---|---|
| `acceptance_criteria` | **구현이 됐나** | 병합 전 |
| 빠진 것 | **실제로 쓰이나** | 출시 뒤 |

### ADR-0019와 다르다

ADR-0019(관측성)는 **"자동화가 못 잡는 판단을 누가 하나"**가 문제였고 빠진 것이 감사
역할이었다. 이건 **"무엇을 알고 싶은지 아무도 안 묻는다"**가 문제이고 빠진 것이 슬롯이다.

| | ADR-0019 | 이 결정 |
|---|---|---|
| 누가 정의하나 | 개발팀 | 제품 |
| 무엇을 보나 | 에러·성능 | 사용 행동 |
| 어디서 시작하나 | 기술 계약 | **요구사항** |

## 결정 1 — `measurement` 슬롯을 필수로 둔다

**필수로 두되 "없음"을 명시하면 충족된다.** `scope_out`이 이미 그 방식이다.

리팩터링이나 내부 도구에는 측정할 것이 없을 수 있다. 그때 슬롯을 비우게 하면 "측정할
것이 없다"와 "아무도 안 물었다"가 구분되지 않는다 — 이 저장소가 침묵 생략을 다루는
방식과 같은 이유다.

## 결정 2 — 이름은 `measurement`다

세 후보를 봤다.

| 후보 | 왜 아닌가 |
|---|---|
| `tracking` | 수단이지 질문이 아니다. 무엇을 알고 싶은지가 아니라 어떻게 잴지를 가리킨다 |
| `success_metric` | `acceptance_criteria`와 "성공"이 겹친다. 가르려는 두 질문이 이름에서 다시 섞인다 |
| **`measurement`** | 중립적이고 겹치지 않는다 |

## 결정 3 — 지표까지만 묻는다

세 수준이 가능했다.

```text
① 목표 지표만                    ← 이것
② 지표 + 이벤트 이름
③ 지표 + 이벤트 이름 + 속성 스키마
```

**뒤로 갈수록 요구사항이 아니라 계약이다.** 이벤트 이름·속성·타입은 `specification`이
고정한다(ADR-0019 · `OBSERVABILITY.md`). 요구사항이 거기까지 요구하면 계약 일을
앞당기고, 계약 고정 단계가 할 판단을 요구사항 단계가 미리 굳혀 버린다.

**지표 없이 이벤트 이름부터 정하면 무엇을 위한 계측인지 아무도 모른다.** 순서가 이쪽이
맞다 — 요구사항이 *무엇을 알고 싶은지*를 묻고, 계약이 *그것을 어떤 이벤트로 잴지*를 정한다.

### `constraints`와 겹치지 않는다

`constraints`가 이미 성능 예산을 담는다. 그래서 "성능은 슬롯이 있는데 왜 사용 행동은
새 슬롯인가"를 물을 수 있다.

**성능은 이미 자리가 있었고 사용 행동은 없었다.** 그리고 둘은 같은 흐름을 탄다 —
요구사항이 무엇을 원하는지 적고(`constraints`의 예산, `measurement`의 지표), 계약이
그것을 잴 방법을 고정한다(임계값, 이벤트 스키마). 새로 만든 것은 흐름이 아니라
**비어 있던 한 칸**이다.

## 나머지는 이미 자리가 있다

| 일 | 어디 |
|---|---|
| 무엇을 알고 싶은가 | `requirements` — **이 결정이 채운다** |
| 이벤트 이름·속성·타입 | `specification` |
| 계측 코드 | `implementation#ui` |
| 검증 | ui 테스트 |

**에러 추적보다 오히려 테스트하기 쉽다.** 에러는 경계에 한 번 붙지만 행동 추적은
컴포넌트 이벤트 핸들러에 붙는다. 클릭하고 spy를 단언하면 기존 ui red-green에 그대로
들어간다. 새 Capability도 새 variant도 필요 없다.

## 하네스 밖인 것

수집한 데이터를 분석해 다음 결정을 내리는 것은 제품 분석이다. 하네스가 책임질 것은
**분석 가능한 데이터가 나오도록 계약을 고정하는 것**까지다 — 이름이 일관되고, 필요한
속성이 빠지지 않고, 계측이 실제로 동작하는지.

## 버린 대안

**1. 권장 슬롯으로 둔다.**
비어 있는 것이 정상이 되어 아무도 안 채운다. 이 슬롯이 없어서 이 이슈가 열렸는데,
있어도 안 채우면 같은 상태다.

**2. `acceptance_criteria`를 확장해 담는다.**
그 슬롯은 **피드백 레이어의 검증 타깃**이다. 병합 전에 판정할 수 없는 항목이 섞이면
게이트가 측정할 수 없는 것을 받게 된다.

**3. 새 Capability나 variant를 만든다.**
계측 코드는 컴포넌트 이벤트 핸들러에 붙고 ui 테스트로 검증된다. 기존 자리가 이미 맞다.

## 대가

**필수 슬롯이 여섯에서 일곱이 됐다.** 모든 요구사항이 한 칸을 더 답해야 한다. "없음"이
허용되지만 그것도 사유를 요구하므로 무게가 아주 없지는 않다.

**게이트가 판정을 요구하는데 러너가 없다.** `measurement`가 수용 기준과 섞였는지는 사람
또는 에이전트가 본다. 케이스는 적어 뒀지만 대조는 자동이 아니다(ADR-0002).

**"출시 뒤에 답이 나온다"를 하네스가 확인하지 않는다.** 지표를 적게 할 뿐 그 지표가
실제로 좋아졌는지는 보지 않는다. 그건 하네스 밖이다.

## 재검토 조건

- `measurement`가 "없음"으로만 채워지는 일이 반복되면. 필수로 둔 것이 형식이 됐다는
  신호다.
- 지표만으로 계약을 고정하기 부족한 사례가 나오면. 결정 3의 수준을 다시 본다.
- 완결성 게이트에 러너가 생기면. `measurement`와 `acceptance_criteria`를 가르는 판정이
  자동화 가능한지 본다.
