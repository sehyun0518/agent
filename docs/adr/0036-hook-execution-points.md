# ADR-0036 — 훅 실행 지점이 플랫폼의 어디에 대응하는가 (C4)

- 상태: 채택
- 날짜: 2026-09-01
- 다루는 축: 승격 조건, 플랫폼 투영
- 관련: ADR-0002(C4) · ADR-0015(승인의 플랫폼 투영) · ADR-0018(승격 판단)

## 맥락

`ADR-0002`의 승격 조건 C4다.

> `before-capability`·`after-capability`·`before-tool`·`after-tool`·`on-evidence`·
> `on-failure` 여섯 지점이 **어느 플랫폼의 어느 확장점에 대응하는지** 문서화돼야 한다.

`ADR-0015`가 승인 축에서 쓴 방법을 그대로 쓴다.

> 이 저장소에는 런타임이 없다. **그런데 플랫폼에는 있다.**

## 조사 — 플랫폼 훅 API

로컬에 실제 사례가 있었다. 공식 플러그인이 훅을 선언한다.

```json
{ "hooks": { "SessionStart": [{ "matcher": "startup|resume|clear|compact",
    "hooks": [{ "type": "command", "command": "node ..." }] }] } }
```

변경 로그에 나오는 이벤트: `PreToolUse` · `PostToolUse` · `UserPromptSubmit` ·
`SessionStart` · `SessionEnd` · `Stop` · `SubagentStop` · `Notification` · `PreCompact`.

**축이 다르다.** 플랫폼은 **도구와 세션**을 중심으로 나누고, 하네스는 **Capability와
증거**를 중심으로 나눈다.

## 대응표

| 하네스 지점 | 플랫폼 확장점 | 지금 붙일 수 있나 |
|---|---|---|
| `before-tool` | `PreToolUse` | ⚠ 확장점은 있다. **검사가 상태를 요구한다** |
| `after-tool` | `PostToolUse` | ⚠ 확장점은 있다. **이 지점을 쓰는 훅이 없다** |
| `before-capability` | `PreToolUse` (matcher `Task`) | ⚠ 근사다. Capability가 항상 서브에이전트로 도는 것이 아니다 |
| `after-capability` | `SubagentStop` · `PostToolUse`(`Task`) | ⚠ 근사이고, **검사 대부분이 판단이다** |
| `on-evidence` | **없음** | 증거를 기록하는 주체가 없어 **사건이 안 난다** |
| `on-failure` | **없음** | 실패를 분류하는 주체가 없어 **사건이 안 난다** |

## 결정 1 — C4는 여섯 중 넷까지만 답할 수 있다. 둘은 순환이다

`on-evidence`와 `on-failure`에 대응점이 없는 것은 **플랫폼의 부족이 아니다.**
증거 기록과 실패 분류는 하네스의 개념이고, 그 사건을 내는 주체가 `execution-state`다.

**C4는 런타임을 만들기 전에 답하라는 조건인데, 두 지점은 런타임이 생겨야 답이 나온다.**
`ADR-0002`가 예상하지 못한 순환이다.

C4의 목적을 다시 보면 답이 좁혀진다.

> 실행 주체 없이 런타임을 만들면 **훅이 다시 프롬프트 규칙으로 흡수된다.**

막으려는 것은 "대응점 없는 훅 위에 코드를 쌓는 것"이다. 그 위험은 **넷에 대해 확인됐고,
둘에 대해서는 그 사건 자체를 런타임이 만든다** — 흡수될 프롬프트 규칙이 아니라
런타임이 정의할 사건이다.

**C4를 "여섯 다 대응점이 있다"로 읽으면 영원히 충족되지 않는다.** "각 지점이 어디에
대응하는지, 대응하지 않으면 왜인지 적혔다"로 읽는다. 이 표가 그것이다.

## 결정 2 — 넷을 막는 것은 확장점이 아니라 **상태**다

`no-auto-chaining`(`before-tool`)이 무엇을 검사하는지 보면 드러난다.

> **현재 실행 중인 변형**이 자기 몫이 아닌 Git 명령을 실행하려 하면 차단한다.
>
> | 실행 중인 변형 | 허용 | 차단 |
> | `commit` | `git add` · `git commit` | `git push` · PR 생성 |
> | `push` | `git push` | `git commit` · PR 생성 |

`PreToolUse`는 **어느 도구를 부르는지**는 알지만 **어느 변형이 도는지**는 모른다.
아무것도 그것을 들고 있지 않기 때문이다.

`after-capability` 둘은 다른 이유로 막힌다. 검사가 판단이다 — "`acceptance_criteria`가
**객관적으로 검증 가능한** 기준 2개 이상인가", "계약에 **모순이나 미정 항목**이 남아
있지 않은가". 확장점이 생겨도 거기서 돌릴 것이 없다.

**그래서 넷 중 셋은 확장점이 아니라 상태·판단이 막고 있다.**

## 결정 3 — 하나는 지금 투영할 수 있다

`no-auto-attribution`은 **상태를 요구하지 않는다.** 커밋 메시지와 PR 본문에 출처 문구가
들어갔는지 보고, 기준은 프로파일의 `git.automaticAttribution`이라는 정적 선언이다.

도구 호출만 보면 판정된다. `ADR-0015`가 승인 축에서 얻은 것과 같은 종류의 강제를
**훅 축에서 처음** 얻을 수 있는 자리다.

**이 ADR에서 만들지는 않는다.** C4가 요구한 것은 문서화이고, 투영은 스크립트를
소비자의 기계에서 돌리는 일이라 결정이 하나 더 필요하다 — 어디에 두고 누가 갱신하는가.
재검토 조건에 적는다.

## 결정 4 — 선언된 이벤트가 틀린 것을 고친다

조사하다 나왔다. `no-auto-attribution`이 **`before-capability`** 로 선언돼 있는데,
검사 대상은 **커밋 메시지와 PR 본문**이다.

`before-capability`는 Capability가 시작할 때 한 번 돈다. **그 시점에는 볼 메시지가
없다.** 메시지는 도구를 부를 때 생긴다.

`before-tool`로 고친다.

### 이벤트 이름을 아무도 대조하지 않고 있었다

훅은 마크다운이고 이벤트를 산문으로 적는다. `before-없는것`이라고 바꿔도 검증이
통과했다.

**이름이 틀리면 실행 주체가 생겼을 때 그 훅은 영영 안 불린다.** 그런데 문서는
`blocking: 예`라고 적혀 있으니 읽는 사람은 막힌다고 믿는다.

목록은 `policy.schema.json`이 갖는다. 검사가 거기서 읽는다 — 옮겨 적지 않는다.

## 버린 대안

**1. 여섯 다 대응할 때까지 C4를 미룬다.**
`on-evidence`·`on-failure`는 런타임이 생겨야 사건이 난다. 영원히 안 끝난다.

**2. `on-evidence`·`on-failure`를 지점 목록에서 뺀다.**
사건이 없으니 지점도 없다는 논리인데, 그 둘이 하네스의 중심 개념이다. 뺀 순간
런타임이 그것을 안 만들어도 아무도 모른다.

**3. 훅을 플랫폼 이벤트 이름으로 다시 쓴다.**
`PreToolUse`를 선언에 적는 안이다. **하네스가 한 플랫폼의 것이 되고**, ADR-0015가
승인 축에서 거부한 것과 같다 — 선언은 중립이고 문법은 플랫폼마다다.

**4. `no-auto-attribution`을 지금 투영한다.**
할 수 있고 값이 크다. 그런데 스크립트를 소비자 기계에서 돌리는 일이라 어디에 두고
누가 갱신하는지가 정해져야 한다. C4가 요구한 것은 문서화이므로 가른다.

## 대가

**C4는 여전히 충족이 아니다.** 넷은 대응점이 확인됐고 둘은 왜 없는지가 적혔다.
"충족"으로 볼지는 `ADR-0002`를 다시 읽는 사람의 판단이고, 이 ADR은 **무엇이 사실인지만
적는다.**

**대응표가 근사를 담고 있다.** `before-capability` ↔ `PreToolUse`(`Task`)는 Capability가
서브에이전트로 돌 때만 맞다. 지금은 메인 에이전트가 직접 도는 경우가 더 많다.

**투영은 아직 하나도 없다.** 승인 축은 ADR-0015가 했지만 훅 축은 여전히 문서뿐이다.

**이벤트 이름 검사는 이름만 본다.** 그 이벤트가 그 훅의 검사와 맞는지는 산문이라
못 본다 — `no-auto-attribution`이 틀려 있던 것을 검사가 아니라 사람이 찾았다.

## 재검토 조건

- `no-auto-attribution`을 투영하기로 하면. 스크립트를 어디 두고 누가 갱신하는지 정한다.
- `execution-state`가 승격되면. `on-evidence`·`on-failure`의 대응점이 그때 생긴다.
- 플랫폼이 Capability 단위 확장점을 내면. 근사 둘이 정확해진다.
