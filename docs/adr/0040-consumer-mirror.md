# ADR-0040 — 생성물을 소비 저장소로 내되, 놓은 것만 관리한다

- 상태: 채택
- 날짜: 2026-09-02
- 다루는 축: 생성 계약, 소비 저장소 계약
- 관련: ADR-0003(생성 미러) · ADR-0016(벤더링 대조) · ADR-0020(배치) · ADR-0039(설정 커맨드)

## 맥락 — 커맨드가 소비 저장소에 닿지 않았다

`init`까지 만들고 나서도 **소비 저장소에서 `/step`을 칠 수 없었다.** 생성기가
하네스 자기 `.claude/`·`.codex/`에만 썼기 때문이다.

실제 상태를 셌다.

```text
하네스   agents 15  skills 16  commands 15
blog     agents 11  skills 11  commands  0
```

겹치는 열한 개를 대조했더니 **둘만 같고 아홉이 달랐다.** 넷은 아예 없었다.
누군가 손으로 복사한 뒤 아무도 갱신하지 않았고, **대조하는 것도 없었다.**

`commands`가 0인 것이 그 결과다. 하네스가 `/init`·`/step`·`/reviews`를 만들어도
저장소는 그것을 받을 경로가 없다.

## 결정 1 — `--check`와 같은 축에 `--into <경로>`를 둔다

소스는 언제나 하네스에서 읽고 **출력 베이스만 옮긴다.** 두 곳에 생성 로직이
생기지 않는다.

```text
npm run generate                        # 하네스 자기 미러
npm run generate -- --into ../blog      # 소비 저장소로
npm run generate -- --check --into ../blog   # 대조만, 안 쓴다
```

## 결정 2 — 고아 정리를 **소비 저장소에서는 매니페스트로 좁힌다**

이게 이 ADR의 핵심이다.

하네스의 `.claude/`는 통째로 하네스 것이라 **생성 집합에 없는 파일을 지워도 된다.**
지금 생성기가 그렇게 한다 — `agentDir`·`skillDir`·`rules`를 훑어 `expected`에 없으면
`rmSync`.

**소비 저장소에 그대로 겨누면 남의 파일을 지운다.** 저장소가 자기 역할·스킬을 둘 수
있고, 그것이 정당하다.

그래서 `.agent-harness/generated.json`에 **우리가 놓은 것을 적어 두고 그것만 본다.**

| 상태 | 무엇 | 어떻게 |
|---|---|---|
| 이번에 냄 | 하네스 것 | 쓴다 |
| 지난번 매니페스트에 있는데 이번엔 안 냄 | 하네스가 뺀 것 | **지운다** |
| 매니페스트에 없는데 거기 있음 | 저장소 것이거나 손 복사본 | **말만 한다** |

세 번째를 지우지 않는 것이 결정이다. 손으로 복사한 것인지 저장소가 일부러 둔 것인지
**하네스는 구분할 수 없고**, 틀렸을 때의 대가가 한쪽만 크다.

**새 패턴이 아니다.** 벤더링이 같은 문제를 이미 풀었다 — 무엇을 우리가 가져왔는지
적어 두고 그것만 대조한다(ADR-0016). 여기서는 방향이 반대일 뿐이다.

## 결정 3 — 매니페스트에 **어느 판이 냈는지**를 남긴다

```json
{ "harness": "0.3.0", "files": [...] }
```

`blog`가 `0.0.0`에 멈춰 있었다. 낡은 채로 오래 남는 것이 실제로 나는 일이므로
**무엇이 놓았는지**를 파일에 적는다. 서브모듈 커밋을 안 보는 `init`의 빈틈(ADR-0039
대가)을 여기서 조금 메운다.

자리는 `.agent-harness/`다 — 프로파일 옆이라 저장소가 한 곳만 본다.

## 버린 대안

**1. 소비 저장소에서도 디렉터리를 훑어 고아를 지운다.**
한 줄 덜 쓴다. 그리고 **저장소의 자기 에이전트를 지운다.** `blog`에 그런 파일이
없었던 것은 운이지 설계가 아니다.

**2. 아무것도 안 지운다.**
안전하지만 하네스가 뺀 에이전트가 소비 저장소에 영원히 남는다. 그 상태가
지금 `blog`고, **아홉 개가 어긋나 있었다.**

**3. 소비 저장소에 생성기를 복사해 거기서 돌린다.**
생성 로직이 두 곳이 된다. 그리고 하네스를 올려도 소비 저장소의 복사본은 안 올라간다 —
**지금 겪고 있는 문제와 같은 모양이다.**

**4. 손 복사본을 발견하면 지운다.**
"매니페스트에 없다"는 "손으로 복사했다"를 뜻하지 않는다. 저장소가 자기 것으로 둔
파일과 구분이 안 된다.

## 대가

**첫 실행이 손 복사본을 덮어쓴다.** 이름이 겹치면 매니페스트 없이도 `emit`이 쓴다.
`blog`의 아홉 개가 그렇게 갱신된다 — 그것이 의도지만, **저장소가 손으로 고쳐 둔
내용이 있었다면 사라진다.** `--check --into`로 먼저 보라고 말하는 것이 지금의 대비다.

**매니페스트가 플랫폼을 건너다닌다.** 저장소에 커밋되므로 Windows에서 낸 것을 macOS에서
읽는 일이 난다. `relative()`가 내는 백슬래시를 그대로 적으면 겹치는 경로가 하나도 없고
**지난번에 놓은 것 전부가 지울 대상이 된다** — 실측 425개 전멸이었다. 기록하는 쪽과 읽는
쪽 양쪽을 POSIX로 맞춘다(#102 리뷰).

**손으로 고칠 파일이다.** "직접 고치지 않는다"고 적어 두었으므로 누군가 고친다. JSON이
깨졌거나 `files`가 배열이 아니면 **없는 것으로 보고 경고만 한다** — 여기서 죽으면 다시
내서 고칠 길까지 막힌다. 안전한 방향은 덜 지우는 쪽이다.

**매니페스트를 지우면 그 뒤로 아무것도 안 지운다.** 그 시점의 생성물이 전부
"관리하지 않는 파일"이 된다. 복구는 다시 한 번 내는 것이다.

**두 저장소가 어긋날 수 있다.** 하네스를 올려도 소비 저장소는 누군가 `--into`를
돌려야 갱신된다. `operations.md` §0의 "조언만" 칸에 들어가는 다섯 번째다 —
**CI가 소비 저장소 쪽 드리프트를 보지 않는다.**

**`.codex/`까지 함께 나간다.** 소비 저장소가 Codex를 안 써도 425개가 놓인다.
플랫폼을 골라 내는 것은 아직 없다.

## 재검토 조건

- 소비 저장소가 둘 이상 붙으면. 갱신을 사람이 기억하는 것이 버티는지 본다.
- 손 복사본을 덮어써서 잃은 내용이 나오면. 첫 실행 전 대조를 강제할지 본다.
- 플랫폼을 골라 내달라는 요구가 나오면. `--into`에 플랫폼 필터를 붙일지 본다.
- 배포 방식이 정해지면(ADR-0001 D9). 이 명령 자체가 배포로 대체될 수 있다.
