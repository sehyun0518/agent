# ADR-0032 — 사람이 흐름을 돌리는 것을 무엇으로 돕는가

- 상태: 채택
- 날짜: 2026-09-01
- 다루는 축: 운영 도구, 생성 산출물
- 관련: ADR-0002(승격) · ADR-0026(commandKey 오타) · `docs/operations.md` §0

## 맥락

이 하네스에는 실행 엔진이 없다. 단계 호출과 증거 기록은 **사람 또는 메인 에이전트**가
한다(ADR-0002). 그 판단은 유지된다 — 승격 조건 넷 중 셋이 미충족이고(ADR-0018), 오늘만
계약이 여러 번 바뀌었다.

**그런데 사람이 돌리기 어렵다.** 단계 하나를 실행하려면 파일 다섯을 연다.

| 무엇을 알려고 | 어디를 여나 |
|---|---|
| 이 단계가 무엇인지 | `workflows/change.yaml` |
| 어떤 증거를 남기는지, 완료 조건이 뭔지 | `capabilities/<id>/capability.yaml` |
| 게이트가 무엇을 보는지 | `workflows/gates/*.md` |
| 도메인 단계가 끼는지 | `profiles/*/profile.yaml` |
| 토큰과 상태가 무슨 뜻인지 | `docs/vocabulary.md` |

`change`는 단계가 **28개**다. `/change` 커맨드는 "워크플로 파일을 읽고 진행하라"까지만
말하고, 교차 참조는 매번 손으로 한다.

## 결정 1 — 읽어서 인쇄하는 도구를 만든다. 실행하지 않는다

```bash
npm run step change logic
```

선언 다섯을 읽어 그 단계에 필요한 것을 한 화면에 모은다 — 게이트와 선행 증거, 남겨야
하는 증거와 완료 조건, 내는 토큰, 프로파일 삽입.

**이것이 런타임이 아닌 이유가 중요하다.**

| | 이 도구 | `execution-state`(미승격) |
|---|---|---|
| 단계를 부르나 | ❌ | ✅ |
| 증거를 남기나 | ❌ | ✅ |
| 상태를 바꾸나 | ❌ | ✅ |
| 게이트를 판정하나 | ❌ | ✅ |
| 선언을 읽어 인쇄하나 | ✅ | — |

`npm run validate`와 같은 부류다 — 선언을 읽는 도구이고, 읽는 것은 승격 조건과 무관하다.
**승격 조건은 잘못된 추상화 위에 코드를 쌓지 않기 위한 것**이고, 인쇄하는 코드는 추상화를
가정하지 않는다.

## 결정 2 — 내용을 복제하지 않는다. 호출할 때 읽는다

커맨드 파일이 순서를 옮겨 적지 않는 원칙과 같다. 브리핑은 **호출 시점에** 선언을 읽으므로
드리프트가 생길 자리가 구조적으로 없다.

그래서 생성 산출물이 아니다. `.claude/commands/step.md`는 스크립트를 가리키기만 하고
내용을 담지 않는다.

## 결정 3 — 붙는지 판정하는 규칙을 여기서 정하지 않는다

프로파일 삽입이 이 단계에 붙는지는 생성기가 이미 판정한다. 처음에 브리핑 쪽에서
`anchorCapability`만 보고 다시 썼더니 **`bugfix`용 삽입이 `change` 브리핑에 섞였다** —
흐름을 안 가렸고 `anchorStep`도 안 봤다.

`extensionApplies`와 `anchoredAt`을 생성기에서 내보내고 양쪽이 같은 함수를 쓴다.
#88에서 쓰기 도구 목록을 두 번 적었던 것과 같은 실수이고 같은 해법이다.

## 결정 4 — 도구 커맨드가 가리키는 스크립트를 대조한다

`TOOL_COMMANDS`는 선언에서 유도되지 않는다 — Capability도 워크플로도 아니기 때문이다.
그래서 이름이 두 곳에 있다: 커맨드의 `script`와 `package.json`의 `scripts`.

없는 스크립트를 가리키면 부른 사람은 **커맨드가 깨졌는지 자기가 틀렸는지 모른다.**
ADR-0026이 `commandKey` 오타에서 본 것과 같은 자리라 같이 검사한다.

## 버린 대안

**1. 단계마다 슬래시 커맨드를 낸다.**
28 × 3 = 84개가 생기고, 커맨드 목록이 흐름 자체보다 커진다. 그리고 워크플로가 바뀔 때마다
파일이 생겼다 없어진다.

**2. 커맨드 본문에 단계 내용을 적는다.**
`/change`가 순서를 옮겨 적지 않는 이유와 같다. 옮겨 적으면 낡는다.

**3. 흐름 상태를 보여준다(`어디까지 왔나`).**
증거를 기록하는 주체가 없어 대부분 빈 화면이 된다. 손으로 증거를 남긴 흐름에서만 의미가
있고, 그 조건이 갖춰지면 그때 만든다.

**4. 아무것도 안 만든다.**
지금 상태다. "시켜서 하면 돌아간다"인데 시키는 쪽의 부담이 단계마다 파일 다섯이다.

## 검증 안 된 선언을 읽는다

`npm run validate`와 다른 점이다. 검증기는 검증하려고 읽지만, 브리핑은 **고치는 중에
부르는 것이 정상 사용**이다 — 단계를 하나 손보고 바로 확인한다.

그래서 스키마가 보장한다고 가정하지 않는다. 깨진 YAML에는 스택 대신 어디가 깨졌는지
내고, 배열 안의 빈 원소를 건너뛴다. ADR-0029가 에스컬레이션 검사에서 적은 것과 같은
자리이고, 이번에도 리뷰가 먼저 짚었다(#92).

## 대가

**여전히 아무것도 강제하지 않는다.** 브리핑을 안 보고 단계를 건너뛰어도 막히지 않는다.
§0 표의 아래 절반은 그대로다.

**게이트 본문은 읽지 않는다.** 머리의 `blocking`·`소비 증거`만 뽑고 판정 조건은 산문이라
파일을 열어야 한다. 조건이 자기신고인 것과 같은 한계다.

**`vocabulary.md`는 안 읽는다.** 토큰 이름을 보여줄 뿐 뜻은 안 붙인다. 어휘를 브리핑에
넣으면 화면이 문서가 되고, 그때는 문서를 읽는 편이 낫다.

## 재검토 조건

- 증거를 기록하는 주체가 생기면. 흐름 상태 보기(버린 대안 3)를 다시 본다.
- 도구 커맨드가 셋 이상이 되면. 지금은 중앙 목록이 하나뿐이라 유도하지 않는 것이 싸다.
- 게이트 조건을 구조화하면. 그때 브리핑이 조건을 그대로 낼 수 있다.
