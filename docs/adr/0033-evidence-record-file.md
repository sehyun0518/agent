# ADR-0033 — 증거 레코드를 어디에 어떻게 쓰는가

- 상태: 채택
- 날짜: 2026-09-01
- 다루는 축: 증거 계약, 외부기억
- 관련: ADR-0018(증거 위치) · ADR-0022(runId) · ADR-0028(동시 실행) · ADR-0032(브리핑)

## 맥락

증거 레코드의 **모양**은 정해져 있다(`docs/vocabulary.md` §5).

```yaml
kind: test.unit.result
status: failed
summary: "3 failed, 12 passed"
artifact: .harness/runs/{runId}/unit.json
producedBy: test-execution#unit
```

**그런데 이 블록이 어느 파일에 사는지는 아무 데도 없다.** `artifact`가 가리키는 원본
파일의 자리는 있는데, 레코드 자신의 자리가 없다.

그래서 아무것도 증거를 대조하지 못한다. `/step`이 "이 단계는 red 증거가 필요하다"까지
말하고 **"그게 있는지"는 못 말한다**(ADR-0032 버린 대안 3).

이 세션이 낸 실패가 그 자리에 있다. 검증이 안 돌았는데 "정상 종료한다"고 커밋 메시지에
적었고, 2줄만 고쳤다고 PR에 적었는데 129줄이 재포맷됐다. **말과 파일을 대조할 수단이
없으면 자기신고가 유일한 기록이다.**

## 결정 1 — 흐름 하나에 파일 하나. `evidence.yaml`에 쌓는다

```text
.harness/runs/{runId}/
  evidence.yaml     ← 레코드가 순서대로 쌓인다
  unit.json         ← artifact가 가리키는 원본
  contract-diff.md
```

**단계마다 파일을 두지 않는다.** 게이트는 흐름 전체에서 앞 단계 증거를 찾으므로 한 번
읽는 편이 맞고, 재시도하면 같은 단계의 레코드가 둘이 되는데 파일이 하나면 **덮어쓸지
말지를 정할 필요가 없다** — 둘 다 남기고 읽는 쪽이 마지막을 본다.

궤적을 지우지 않는 것은 ADR-0023이 `attempt`를 넣은 이유와 같다. **재시도로 통과한 것과
한 번에 통과한 것은 다른 사건이다.**

**덧붙이기가 안전한 것은 동시 실행을 금지했기 때문이다**(ADR-0028). 한 체크아웃에서
활성 흐름이 하나라 같은 파일을 둘이 열지 않는다.

**세션을 넘으면 같은 파일에 이어 쓴다.** `runId`가 같으면 디렉터리가 같다(ADR-0022).

## 결정 2 — 레코드에 `step`을 넣는다

`producedBy`로는 단계를 못 가린다. 실제로 **여덟 곳이 충돌한다.**

```text
test-execution#unit         → unit-red · unit-green
test-execution#ui           → ui-red · ui-green
test-execution#integration  → integration-red · integration-green
test-execution#e2e          → e2e-red · e2e-green
                              (change · bugfix 각각)
```

게이트는 단계로 찾는다.

```yaml
expect:
  - evidence: test.unit.red-proof
    status: confirmed
    from: unit-red        # ← 단계 id
```

**`from: unit-red`를 `producedBy: test-execution#unit`에서 해결할 수 없다.**

두 필드는 다른 축이다.

| 필드 | 답하는 것 |
|---|---|
| `producedBy` | **누가** 만들었나 — 역할 |
| `step` | 흐름의 **어디**인가 — 위치 |

**둘 다 둔다.** 워크플로 단계는 `step`에서 `producedBy`를 유도할 수 있지만, 프로파일이
끼운 단계는 워크플로 파일에 없어서 프로파일을 읽어야 한다. 그리고 **증거는 외부기억이다** —
나중에 읽는 사람이 워크플로 파일 없이도 무슨 일이 있었는지 알아야 한다.

`kind`와 `status`로 가르는 안도 봤다. 같은 변형이라 선언된 `kind`가 같고, `status`로
구분하는 것은 추론이다. ADR-0030이 워크플로를 단계 집합에서 추론하는 것을 거부한 것과
같은 모양이다 — **추론이 가장 필요한 자리에서 추론이 가장 안 된다.**

## 결정 3 — 읽는 쪽이 `runId`를 찾는 방법만 정한다. 발급은 정하지 않는다

발급 주체는 `execution-state`이고 승격되지 않았다(ADR-0028).

읽는 쪽은 이렇게 찾는다.

1. `--run <id>`로 받으면 그것
2. 없고 `.harness/runs/` 아래 디렉터리가 **하나면** 그것
3. 여럿이면 목록을 보여주고 멈춘다

**"가장 최근"을 고르지 않는다.** 그것은 판단이고, 틀리면 **다른 흐름의 증거로 통과했다고
말하게 된다** — 게이트가 막으려는 바로 그 일이다.

## 결정 4 — 브리핑은 있는지 없는지만 말한다. 판정하지 않는다

`/step`이 `expect`마다 대조해 표시한다.

```text
  expect  test.unit.red-proof = confirmed  (from: unit-red)
          ⚠ 그 증거가 없다
```

**막지 않는다.** 게이트 판정은 성립 조건이 산문이라 여전히 사람이 한다 —
`moot`이 정당한지, red가 예상한 이유인지는 파일에 없다.

그래도 **말과 파일이 갈리는 것은 이제 보인다.** 자기신고 문제 전체를 푸는 것은 아니고
**대조할 대상이 처음 생기는 것**이다.

## 버린 대안

**1. 단계마다 파일(`{stepId}.yaml`).**
재시도 시 덮어쓸지 이름을 늘릴지 정해야 하고, 흐름 전체를 보려면 디렉터리를 걷는다.
게이트가 앞 단계를 찾는 것이 기본 동작이므로 한 파일이 맞다.

**2. `producedBy`의 뜻을 단계로 바꾼다.**
"누가 만들었나"를 잃는다. 그리고 기존 예시와 문서가 전부 역할을 적고 있어 의미 변경이다.

**3. `kind`+`status`로 단계를 추론한다.**
같은 변형이라 `kind`가 같다. 추론이고, 틀리면 다른 단계의 증거로 통과한다.

**4. 레코드 스키마 파일을 만든다.**
`.harness/`는 gitignore이고 검증기는 선언을 본다. 실행 산출물을 검증기가 검사하기
시작하면 그 경계가 흐려진다. 모양은 `event.schema.json`의 `evidence`가 갖고 어휘가
설명한다.

**5. 계속 미룬다.**
"증거를 기록하는 주체가 없으니 자리도 미룬다"가 지금 상태다. 그런데 **자리를 안 정하면
사람이 손으로도 못 남긴다.** 주체가 없는 것과 자리가 없는 것은 다른 문제다.

## 대가

**아무도 기록하지 않는다.** 자리를 정했을 뿐 남기는 것은 사람이다. `operations.md` §2.4의
"증거를 정말 남겼는지"는 그대로 남는다.

**빈 화면이 기본이다.** 지금 `.harness/runs/`가 없어서 브리핑은 전부 `⚠ 없다`를 낸다.
손으로 남기기 시작해야 의미가 생긴다.

**게이트 조건은 여전히 자기신고다.** 증거가 **있는지**는 보이지만 그 증거가 **맞는지**는
안 보인다. `moot` 세 조건, `manual-result` 세 조건이 그대로다.

**레코드 형식을 강제하지 않는다.** 망가진 `evidence.yaml`은 읽는 쪽이 건너뛰고 그 사실을
말한다. 검증기가 실행 산출물을 검사하지 않는다는 경계 때문이다(버린 대안 4).

## 재검토 조건

- 손으로 증거를 남긴 흐름이 실제로 생기면. 형식이 쓸 만한지, 무엇이 빠졌는지 본다.
- `execution-state`가 승격되면. `runId` 발급과 덧붙이기 주체가 생기므로 결정 3을 다시 본다.
- 재시도가 실제로 여러 번 나면. 마지막을 본다는 규칙이 맞는지, `attempt`를 레코드에도
  둘지 본다.
