# ADR-0016 — 벤더링 드리프트를 무엇으로 언제 잡는가

- 상태: 채택
- 날짜: 2026-09-01
- 다루는 축: 벤더링, 검사 주기
- 관련: ADR-0008(서드파티 스킬 벤더링) · ADR-0006(생성 미러)

## 맥락

ADR-0008이 벤더링 파일의 바이트 일치를 요구하고 비교 범위·정규화 규칙까지 고정해
뒀는데 **대조하는 도구가 없었다.** 사람이 손으로 봤다.

두 번 어겼고 **둘 다 우연히 잡혔다.**

| | 무엇 | 언제 발견 |
|---|---|---|
| #24 | `markdownlint --fix`가 벤더링 파일 6개를 고침 | **한 달 뒤** (#28) |
| #27 | 옮겨 적다 규칙 5개를 건드림 | 같은 PR 안에서, 우연히 |

셋째가 나오면 또 사람이 잡아야 한다.

## 불일치는 두 가지다

이 구분이 결정의 축이다.

| | 무엇 | 무엇이 필요한가 |
|---|---|---|
| **드리프트** | 우리가 고쳤다 | 벤더링 시점 기록. **네트워크 불필요** |
| **갱신** | 상류가 바뀌었다 | 상류를 받아 봐야 한다. **네트워크 필요** |

대조 하나로는 둘을 구분할 수 없다. 그런데 **비용도 주기도 다르다** — 드리프트는 매
PR에서 막아야 하고, 갱신은 알면 되지 막을 일이 아니다.

## 결정

### 1. 두 검사를 나눈다

**드리프트 — 벤더링 시점에 기록한 해시와 대조한다. `npm run check`에 넣는다.**

네트워크를 쓰지 않으므로 오프라인에서도 돌고 상류 장애가 우리 PR을 막지 않는다.
매 PR에서 실행되고 어긋나면 병합을 막는다.

**갱신 — 상류를 받아 대조한다. 이 결정에서 구현하지 않는다.**

주기적으로 돌려 이슈를 여는 것이 맞지만, 드리프트 검사와 성격이 다르고 실패가 병합을
막아서는 안 된다. **여기서 여는 구멍을 적어 둔다.**

> 기록은 벤더링 시점의 **로컬 파일**에서 나온다. 옮겨 적다 틀린 것은 틀린 채로
> 기록되므로 이 검사가 잡지 못한다 — #27이 정확히 그 경우다. 그것을 잡으려면
> 상류를 받아야 한다.

즉 이 결정은 **두 실패 중 하나만 막는다.** 나머지 하나는 열려 있고, 그 사실이
`#33`에 남는다.

### 2. 종류는 마커가 아니라 선언으로 가른다

ADR-0008은 종류 B와 C를 마커 유무로 갈랐다. 그러면 **마커를 지우는 것만으로 검사를
빠져나간다** — "우리가 새로 쓴 파일"이 되기 때문이다.

`metadata.vendored: body-rewritten`을 선언한 팩만 종류 C다. 선언 없이 마커가 없으면
드리프트다.

```text
metadata.source 없음                         → 우리 것. 대조하지 않는다
metadata.source + vendored: body-rewritten   → 종류 C. SKILL.md 본문을 대조하지 않는다
metadata.source, 선언 없음                    → 종류 B. 마커가 반드시 있어야 한다
```

`reactlynx-best-practices`가 이미 그 선언을 갖고 있었다. 새 규약이 아니라 있던 것을
검사가 읽게 한 것이다.

**선언을 읽을 수 없으면 "우리 것"으로 보지 않는다.** `SKILL.md`는 전부 frontmatter를
갖고 있으므로 못 읽는 것 자체가 이상한 상태다. 흘려보내면 그 팩이 대조에서 통째로
빠진다 — 기존 팩은 기록에 남아 "파일이 없다"로 걸리지만 **새 팩은 기록에 들어가지도
않는다.** 조용한 우회라 사유를 내고 실패로 다룬다.

### 3. 양방향으로 본다

내용이 바뀐 것만 보면 **지우거나 더해서 빠져나갈 수 있다.** 기록에 있는데 파일이 없는
것도, 파일이 있는데 기록에 없는 것도 드리프트다.

### 4. `SKILL.md`의 frontmatter도 기록한다

마커 밖이지만 ADR-0008이 상류 키의 값까지 같기를 요구한다. 본문만 보면 frontmatter를
고치는 것이 검사를 통과한다.

## 이 검사가 처음 돌자 두 파일이 걸렸다

`react-best-practice`와 `react-native-skills`의 frontmatter에 `license`·`metadata`가
**두 번씩** 있었다. `source`를 넣을 때 기존 블록에 합치지 않고 새로 붙인 것이다.

```yaml
license: MIT
metadata:
  author: vercel
  version: "1.0.0"
license: MIT              # ← 중복
metadata:                 # ← 중복
  author: vercel
  source: https://...
  version: "1.0.0"
```

**YAML 중복 키라 파싱이 실패한다.** 두 스킬이 플랫폼에서 로드되지 않고 있었고, 아무
검사도 그것을 보지 않았다. 중복 블록을 지워 고쳤다 — 두 번째가 첫 번째의 상위집합이라
첫 블록만 지우면 된다.

이것이 `#27`이 남긴 흔적인지 다른 경로인지는 알 수 없다. 다만 **검사가 없는 동안 무엇이
쌓이는지를 보여준다.**

## 검사를 만들고 CI에 안 넣을 뻔했다

CI는 `npm run check`를 부르지 않고 단계를 따로 나열한다. 벤더링 검사를 `check`에
넣었는데 CI 목록에는 안 넣었다. 손으로 찾았다 — **못 찾았으면 그 검사는 로컬에서만
돌고 병합을 막지 못했을 것이다.**

두 파일에 있는 같은 목록이라 갈라진다. `check`에 있는 명령이 CI에 있는지 검사한다.

**한 방향만 본다.** CI에 더 있는 것은 정상이다 — `npm ci` 같은 준비 단계도, 로컬에서
돌릴 일이 없는 전체 재생성 대조도 CI에만 있어야 한다. 위험한 쪽은 반대다.

## 버린 대안

**1. 상류 대조를 `npm run check`에 넣고 네트워크 실패는 통과로 처리한다.**
오프라인에서 조용히 통과한다. "검사가 돌았다"와 "검사가 못 돌았다"가 구분되지 않으면
그 검사는 있으나 마나다 — 이 저장소가 침묵 생략을 다루는 방식과 같은 이유다.

**2. 기록 없이 상류만 본다.**
매 PR이 네트워크에 의존하고 상류 장애가 우리 병합을 막는다. 드리프트는 로컬 사실인데
그것을 알기 위해 외부에 나가는 것도 맞지 않는다.

**3. 마커 유무로 종류를 가른다 (ADR-0008 그대로).**
검사가 없을 때는 문제가 아니었다. 검사가 생기면 그것이 곧 회피 경로가 된다.

## 대가

**`--record`는 무엇이든 통과시키는 문이다.** 벤더링 파일을 고치고 다시 기록하면 검사가
통과한다. 막을 방법은 **기록 파일을 커밋 대상으로 두어 그 diff가 리뷰에 보이게 하는
것**뿐이다 — 생성 미러가 같은 성질을 갖고 같은 방식으로 다뤄진다(ADR-0006).

**두 실패 중 하나만 막는다.** 위 결정 1에 적은 그대로다.

**기록 파일이 크다.** 184개 항목이고 벤더링할 때마다 통째로 바뀐다. 리뷰에서 읽는
것은 "몇 개가 바뀌었나"이지 해시 값이 아니다.

## 재검토 조건

- 상류 대조를 붙일 때가 되면. 주기와 알림 방식(이슈 자동 생성 등)을 그때 정한다.
- `--record`를 거쳐 드리프트가 들어온 사례가 나오면. 리뷰만으로 부족하다는 신호다.
- 벤더링 팩이 늘어 기록 파일이 리뷰 불가능해지면. 팩별로 나누는 것을 본다.
