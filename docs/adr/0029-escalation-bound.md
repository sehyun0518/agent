# ADR-0029 — 무엇에 상한이 없는가

- 상태: 채택
- 날짜: 2026-09-01
- 다루는 축: 실패 처리, 수량
- 관련: ADR-0024(수량 축을 안 더한다) · ADR-0015(승인의 플랫폼 투영) · ADR-0002(승격) · #85

## 맥락 — #85의 전제가 틀렸다

#85가 이렇게 열었다.

> Capability 여덟이 전부 `transient` 실패에 `action: retry`를 선언합니다.
> **몇 번까지인지가 없습니다.**

**있다.** `capability.schema.json`이 이미 묶고 있다.

```json
"transient": {
  "properties": {
    "action": { "const": "retry" },
    "maxAttempts": { "type": "integer", "minimum": 1, "maximum": 3, "default": 2 }
  }
}
```

그리고 여덟이 전부 `maxAttempts: 2`를 명시한다. 스키마 밖으로 나갈 수도 없다 — 최대 3이다.

**분류마다 `action`이 `const`인 것도 중요하다.** `retry`는 `transient`에만 붙을 수 있고,
`policy-denied`는 `halt`로 고정돼 있다. 스키마 주석이 그 이유를 적어 뒀다.

> 재시도 불가. **정책 거부를 재시도로 우회할 수 없게 스키마가 고정한다.**

그래서 **재시도는 구조적으로 유한하다.** 단계 수가 유한하고 단계마다 3회 이하다.

## 그러면 무엇이 안 묶였나 — 에스컬레이션이다

`contract-violation`은 `escalate`이고 `escalateTo`가 다음 자리를 가리킨다. **횟수 필드가
없다.** 사슬이 돌면 끝나지 않는다.

지금 여덟은 전부 종점에 닿는다.

```text
implementation → specification → requirements → orchestrator
test-design    → specification → requirements → orchestrator
test-execution → test-design   → specification → …
documentation · git-operations · review · requirements → orchestrator
```

**그런데 `requirements`를 `implementation`으로 바꿔도 아무 일도 일어나지 않았다.**
없는 Capability를 가리켜도 마찬가지였다. **끝난다는 것이 사실이지 규칙이 아니었다.**

## 결정 1 — 에스컬레이션이 끝나는지 검사한다

두 가지를 본다.

| 검사 | 무엇 |
|---|---|
| 순환 | 사슬이 종점에 안 닿고 돌면 실패 |
| 없는 대상 | `escalateTo`가 Capability도 `orchestrator`도 아니면 실패 |

**`orchestrator`가 종점이다.** Capability가 아니라 조정자이고, 사슬을 더 넘기지 않고
사람에게 올린다. `escalateTo`를 안 적으면 기본값이 그것이다.

없는 대상을 순환으로 세지 않는다. 두 검사가 나눠 갖고 겹치지 않는다 — `findMissingScaffolds`와
`findMissingMootBranches`가 계층을 나눠 가진 것과 같다.

### 스키마를 믿지 않는다

`action`이 `const: "escalate"`이므로 다른 값은 통과하지 못한다. 그래도 이 검사는
`action`을 직접 본다.

**검증기는 스키마 검증과 독립적으로 돌기 때문이다.** `loadCapabilities()`가 `id`만
있으면 문서를 담고, 스키마에서 떨어진 문서도 그 맵에 들어온다.

확인했다. `action`을 `halt`로 바꾸고 `escalateTo`를 순환하게 두니 스키마 위반과 함께
"에스컬레이션이 돈다"가 **같이** 났다. 그 Capability는 에스컬레이션을 하지 않는데도
사슬로 세어진 것이다 — **틀린 지적 하나가 맞는 지적 옆에 붙는다**(#89 리뷰).

이 세션이 같은 자리를 한 번 봤다. `checkWorkflowExtensions`가 망가진 워크플로에서
터져 다른 파일의 검증을 통째로 죽였다. **스키마가 막아준다는 가정이 검증기 안에서는
성립하지 않는다.**

**이 검사는 지금 아무것도 막지 않는다.** 여덟이 이미 종점에 닿는다. 현재 상태를 규칙으로
바꾸는 것이다.

## 결정 2 — 쓰기·토큰 축은 여전히 더하지 않는다

ADR-0024 결정 2의 판단을 유지한다. **근거가 하나 늘었다.**

ADR-0015가 승인 축에서 강제를 얻은 방법은 **선언을 플랫폼 permission 런타임에 투영하는
것**이었다. 같은 것을 수량에 할 수 있는지 봤다.

**없다.** 생성되는 권한 설정은 명령 패턴 목록뿐이다.

```json
{ "permissions": { "ask": ["Bash(git push:*)"], "deny": ["Bash(rm -rf:*)"] } }
```

`ask`도 `deny`도 **몇 번인지를 모른다.** Codex 쪽도 같다. 세려면 상태를 들고 있는 훅이
있어야 하고, 그것이 `hook-runtime`과 `execution-state`다(ADR-0002).

**투영할 곳이 없으면 선언은 주석이 된다.** ADR-0024가 "아무도 세지 않는 숫자"라고 부른
것이고, 조사가 그 판단을 뒷받침한다.

## 결정 3 — `maxAttempts`가 세어지지 않는다는 것을 적는다

ADR-0024 결정 2가 이렇게 적었다.

> 지금 선언에 숫자를 적으면 **아무도 세지 않는 숫자가 남는다.**

**그런 숫자가 이미 있었다.** `maxAttempts: 2`가 여덟 곳에 있고 세는 주체가 없다. ADR-0024는
새 숫자를 막았지만 있는 숫자를 보지 않았다.

지우지 않는다 — 계약으로서는 맞다. 스키마가 상한을 3으로 묶는 것은 **런타임이 생겼을 때
무엇을 지켜야 하는지**를 고정하는 일이고, ADR-0023이 `attempt`를 계약 필드로 올린 것과
같은 자리다.

**대신 세어지지 않는다는 것을 `operations.md` §2.4에 적는다.** ADR-0024가 축을 빼면서
그 대가를 기록하지 않았다.

## 버린 대안

**1. `escalateTo`에 `maxEscalations`를 더한다.**
세는 주체가 없다. 결정 2와 같은 이유이고, 순환 검사는 세지 않고도 끝남을 보장한다 —
그래서 이쪽이 더 강하다.

**2. `maxAttempts`를 지운다.**
아무도 안 세니 주석이라는 논리인데, 계약은 런타임이 생겼을 때의 약속이다. 지우면 그때
다시 정해야 하고, 그 사이 상한이 3이라는 사실이 사라진다.

**3. 순환을 워크플로 그래프에서 본다.**
에스컬레이션은 워크플로 순서와 다른 축이다. `change.yaml`의 단계 순서가 아니라 실패했을
때 어디로 가는지이고, 그 선언은 capability에 있다.

**4. 아무것도 안 한다.**
#85의 전제가 틀렸으니 닫는 것도 답이다. 그런데 조사하다 **진짜 안 묶인 경로**가 나왔고,
그것이 이슈가 찾던 것이다.

## 대가

**검사가 지금은 아무것도 막지 않는다.** 여덟이 이미 종점에 닿는다. ADR-0028의 격리 검사와
같은 자리다 — 현재 상태를 고정한다.

**쓰기·토큰은 여전히 안 묶인다.** 의도한 것이고 §2.4에 적는다.

**`escalate`가 실제로 몇 번 일어났는지는 아무도 모른다.** 순환은 막지만 "같은 사슬을 열
번 돌았다"는 여전히 안 보인다. 그것은 관측이고 #83이다.

## 재검토 조건

- `hook-runtime`이나 `execution-state`가 승격되면. 수량을 셀 주체가 생기므로 결정 2를
  다시 본다.
- 플랫폼 권한에 수량 축이 생기면. ADR-0015식 투영이 가능해진다.
- 에스컬레이션이 실제로 반복되면. 순환이 아닌데 여러 번 도는 경우이고, 그때 횟수가
  필요한지 본다.
