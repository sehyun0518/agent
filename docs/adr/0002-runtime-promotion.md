# ADR-0002 — 실행 코드화 승격 조건

- 상태: 제안 (승격 전)
- 날짜: 2026-08-04
- 선행: [ADR-0001](./0001-capability-structure.md) D2

## 배경

ADR-0001 D2는 런타임화를 단계적으로 하기로 정했다. 1단계는 선언(YAML manifest +
JSON Schema)과 검증·생성 CLI만 만들고, 실행 코드는 계약이 안정된 뒤로 미뤘다.

1단계가 끝난 지금 상태는 이렇다.

| 있는 것 | 없는 것 |
|---|---|
| Capability·Profile·Workflow·Policy·Telemetry 스키마 | `hook-runtime` — 훅을 실제로 실행하는 것 |
| 어휘 등록부와 검증기 | `policy-engine` — 런타임 정책 판정 |
| 미러 생성기와 드리프트 게이트 | `execution-state` — 증거 저장·조회 |
| 정책 7종 선언 | `capability-registry` — 동적 해석 |
| 조정자 본체(프롬프트) | `orchestrator` 실행 코드 |

정책 7종 중 **3종만 정적 검사로 강제되고 4종은 훅 런타임을 기다린다**
(`policies/README.md`의 ✅/⏳).

## 결정

아래 조건이 **전부** 충족되기 전에는 실행 코드를 만들지 않는다.

### C1. manifest 계약이 한 분기 이상 바뀌지 않았다

`capability.schema.json`·`profile.schema.json`·`workflow.schema.json`에 **구조 변경**이
없어야 한다. 필드 추가는 무방하지만, 필드 의미가 바뀌거나 분리되는 일은 계약이 아직
굳지 않았다는 뜻이다.

> 이 조건이 붙은 이유: Phase 4에서 `chaining.autoInvoke` 하나가 "나가는 호출"과
> "들어오는 자동 진행"을 뭉뚱그리고 있던 게 드러나 두 필드로 갈라졌다. 런타임을
> 먼저 만들었다면 그 잘못된 추상화 위에 코드가 쌓였을 것이다.

### C2. 두 번째 도메인 프로파일이 실제로 붙었다

`profiles/frontend/` 말고 다른 도메인 프로파일이 하나 더 있고, 그것을 붙이면서
core Capability를 고칠 필요가 없어야 한다.

프로파일 분리가 실제로 작동하는지는 두 번째 프로파일이 붙어봐야 안다. 하나만 있는
동안은 "도메인 무관"이 검증되지 않은 주장이다.

### C3. 소비 저장소가 하나 이상 실제로 연결됐다

`.agent-harness/profile.yaml`을 가진 저장소가 실제로 이 하네스를 써야 한다.
`commands`·`conventions`·권한 축소가 현실에서 충분한지는 예시가 아니라 실사용이 답한다.

### C4. 훅 실행 지점이 특정됐다

`before-capability`·`after-capability`·`before-tool`·`after-tool`·`on-evidence`·
`on-failure` 여섯 지점이 **어느 플랫폼의 어느 확장점에 대응하는지** 문서화돼야 한다.

지금은 훅이 마크다운 명세로만 있고 실행 주체가 없다. 실행 주체 없이 런타임을 만들면
훅이 다시 프롬프트 규칙으로 흡수된다.

## 승격 시 순서

조건이 충족되면 이 순서로 만든다. 앞의 것이 뒤의 것에 의존하지 않는다.

1. **`execution-state`** — 증거 기록·조회. 가장 아래층이고 나머지가 전부 이걸 쓴다.
2. **`hook-runtime`** — 훅 실행. ⏳ 정책 4종이 여기서 몸을 얻는다.
3. **`policy-engine`** — 런타임 정책 판정. `policy-decision` 증거를 만든다.
4. **`capability-registry`** — manifest 동적 해석.
5. **`orchestrator`** — 조정 루프. 마지막인 이유는 위 넷이 없으면 조정할 것이 없기 때문이다.
6. **`test-kit`** — `tests/`·`evals/` 러너.

이 시점에 워크스페이스 도구(pnpm workspace 등)를 도입한다. 지금 루트
`package.json` 하나로 충분한 이유는 실행 코드가 없기 때문이다.

## 승격하지 않기로 할 수도 있다

조건이 충족돼도 선언만으로 충분하다고 판단되면 승격하지 않는다. 현재 구조는
Claude Code·Cursor·Codex의 네이티브 서브에이전트가 실행 주체이고, 검증기가 정적
불변식을 강제한다. 이 조합이 실사용에서 충분하다면 런타임은 순수 비용이다.

승격을 결정하는 신호는 "코드가 있으면 멋있다"가 아니라 **"프롬프트로는 지켜지지
않는 규칙이 반복해서 깨진다"** 이다.

## 결과

- 잘못된 런타임 추상화를 미리 굳히지 않는다.
- ⏳ 정책 4종은 그때까지 **강제되지 않는다.** 이 사실을 `policies/README.md`가 표로
  드러내므로, 강제되는 것처럼 오해하지 않는다.
- 선언이 먼저 있으므로 승격 시 런타임은 이 문서들의 구현체가 된다 — 새로 설계하지 않는다.
