# ADR-0037 — 저장소를 존중하되 빠진 것을 알려준다

- 상태: 채택
- 날짜: 2026-09-02
- 다루는 축: 소비 저장소 계약, 조언
- 관련: ADR-0026(툴체인은 저장소가 선언) · ADR-0035(소비 프로파일 읽기) · `AGENT.md`

## 맥락

`blog`에 하네스를 돌려 보니 **명령 넷을 선언하고 `testing.layers`는 하나도 안 적었다.**

```yaml
commands:
  test.unit:        { command: "pnpm exec vitest run packages/utils ..." }
  test.component:   { command: "pnpm exec vitest run packages/ui ..." }
  test.integration: { command: "..." }
  test.e2e:         { command: "..." }
# testing.layers: 없음
```

**아무도 아무 말을 안 했다.** 그래서 두 곳이 곤란해진다.

- 테스트를 **쓰는** 단계(`test-design`)가 `vitest`인지 `jest`인지, 파일 이름을 무엇으로
  할지 모른다
- 브리핑이 도메인 프로파일의 값을 **저장소의 것처럼** 보여준다 — 어느 쪽인지 구분이 없다

## 결정 1 — 막지 않는다. 조언한다

저장소가 자기 도구를 고르는 자리다. 요구하면 **하네스가 `vitest`를 알게 되고**, 그 순간
도메인 무관이라는 주장이 무너진다.

> 공용 하네스에 특정 저장소의 **명령·경로**를 넣지 않는다.
>
> — `AGENT.md`

ADR-0026이 툴체인에서 내린 판단과 같다 — **저장소가 자기 선행조건을 아는 유일한 쪽이다.**

`operations.md` §0의 "조언만" 칸에 들어간다. `version-advice`·`npm run reviews`에 이은
세 번째다.

### 검증기에 조언 채널을 만든다

지금까지 `fail` 하나뿐이었다. **"말은 해야 하는데 막으면 안 되는 것"을 담을 자리가
없었다.** 조언은 종료 코드를 바꾸지 않는다.

```text
4건의 조언 — 막지 않는다:
  · .agent-harness/profile.yaml
      testing.layers.unit가 없다. frontend은 이렇게 쓴다 — 라이브러리 vitest / 파일 …
```

## 결정 2 — 출처는 하네스가 아니라 도메인 프로파일이다

하네스는 `vitest`를 모른다. **`profiles/frontend`가 안다.** 하네스는 그것을 옮길 뿐이다.

```text
소비 저장소에 testing.layers.<layer>가 없다
  → 도메인 프로파일이 그 계층에 무엇을 쓰는지 보고 출처와 함께 보여준다
  → 도메인에도 없으면 빠졌다는 것만 말한다 (지어내지 않는다)
```

**도메인에도 없는 계층은 그 자체가 신호다.** blog의 `component`가 그랬다 — 이름이 코어
어휘에 없어서 어느 도메인도 모른다.

### 어느 도메인인지 정하지 않는다

**소비 프로파일에 도메인을 가리키는 자리가 없다.** `kind: repository`뿐이고 어느 도메인을
따르는지 선언하지 않는다.

하네스가 "이 저장소는 프론트엔드"라고 단정하면 **그것이 곧 도메인을 아는 것**이다.
그래서 **있는 도메인을 전부 출처와 함께 보여주고 고르는 것은 사람이 한다.**

지금은 도메인이 하나뿐이라 한 줄로 나온다. C2가 충족되면 여러 줄이 되고, 그때 이 방식이
쓸 만한지 드러난다.

## 결정 3 — 브리핑이 제안과 선언을 구분한다

`testLayerFor`가 프로파일을 순서대로 보고 **처음 찾은 것**을 냈다. 소비 저장소가 안
적었으면 도메인의 값이 그대로 나왔고, **읽는 사람은 자기 저장소가 그렇게 선언한 줄
안다.** blog가 정확히 그 상태였다.

```text
이 계층의 규약  (제안)
  이 저장소는 안 적었다. frontend이 쓰는 것을 보여준다
  라이브러리  vitest
```

`kind`로 가른다 — `domain`에서 왔으면 제안이다.

**배열 순서에 기대지 않는다.** 처음에는 소비 프로파일을 앞에 두는 것으로 풀었는데,
그것은 부르는 쪽이 순서를 지켜야 성립한다. `kind`로 두 번 훑는다 — `repository` 먼저,
없으면 `domain`.

`commandFor`도 같은 의존을 갖고 있었다. `testLayerFor`만 고치고 넘어갔더니 **테스트에서
도메인을 앞에 두자 도메인의 명령이 저장소 것을 이겼다**(#99 리뷰). 같은 규칙을 쓴다.

## 버린 대안

**1. `testing.layers`를 `kind: repository`에 요구한다.**
막는 것이고, 저장소가 아직 안 정한 상태를 실패로 만든다. `findTestLayerConflicts`가
명령을 요구하는 것과 다르다 — 명령은 "그 계층을 쓴다"고 선언한 뒤의 필수품이지만,
라이브러리는 저장소의 선택이다.

**2. 하네스가 기본 라이브러리를 갖는다.**
`vitest`를 코어에 적는 순간 도메인 무관이 무너진다. 그리고 도메인마다 다르다.

**3. 소비 프로파일에 `domain: frontend`를 더한다.**
어느 도메인인지가 분명해져 제안이 하나로 좁혀진다. 그런데 **스키마 변경이고 C1을 건드린다.**
그리고 지금 도메인이 하나라 그 필드가 무엇을 가르는지 볼 수 없다 — C2 뒤에 본다.

**4. 아무것도 안 한다.**
지금 상태다. 실제 저장소가 계층을 하나도 안 적었고 아무 말도 안 나왔다.

## 대가

**조언은 안 봐도 그만이다.** 종료 코드를 안 바꾸므로 CI에서 초록으로 지나간다. 그것이
이 결정의 내용이지만, **아무도 안 읽으면 없는 것과 같다.**

**어느 도메인인지 여전히 모른다.** 도메인이 둘이 되면 제안이 둘 다 나오고, 고르는 것은
사람이다. 자동으로 좁히려면 버린 대안 3이 필요하다.

**계층 이름이 틀린 것과 안 적은 것이 같은 메시지로 나온다.** `component`처럼 어휘에 없는
이름은 "도메인에도 없다"로 나오는데, 그것은 오타 신호이기도 하다. 명령 키 검사가 그쪽을
따로 짚으므로 둘을 합쳐 읽으면 구분된다.

## 재검토 조건

- 두 번째 도메인 프로파일이 생기면(C2). 제안이 여럿일 때 쓸 만한지, 버린 대안 3이
  필요한지 본다.
- 조언을 아무도 안 읽는 것이 관측되면. 그때 막을지 다시 본다.
- 소비 저장소가 계층을 적기 시작하면. 조언이 사라지는지 보고, 안 사라지면 형식이 문제다.
