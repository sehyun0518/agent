# ADR-0010: 프로젝트 상수는 수동 실행 역할 셋이 정한다

- 상태: accepted
- 날짜: 2026-08-22
- 관련 이슈: #36

## 배경

하네스가 프로젝트 상수를 **읽기만 하고 만들지 않았다.**

요구사항 스키마가 이렇게 적어뒀다.

> 디자인 시스템·토큰·컴포넌트 컨벤션은 느리게 변하는 프로젝트 상수(지식 레이어)다.
> 작업마다 다시 물어 채울 요구사항이 아니라 `DESIGN.md`에 **한 번 박아두고** 모든
> 작업이 참조한다.

그 "한 번"을 하는 주체가 없었다. `profiles/frontend/knowledge/DESIGN.md`는 29줄짜리
골격에 `<!-- TODO -->`만 있다.

`specification`도 마찬가지다. "기존 코드베이스를 먼저 탐색합니다 — 재사용 가능한 타입,
공유 컴포넌트, 네이밍/폴더 컨벤션을 찾습니다"라고 하는데, greenfield에서는 찾을 게 없다.
그러면 계약 고정 단계가 즉석에서 정하게 된다.

소비 쪽만 있고 생산 쪽이 없었다.

## 결정

### 1. Capability가 아니라 프로파일 도메인 역할이다

"프로젝트 상수를 정한다"는 행위는 도메인 무관하지만, **무엇이 상수인지**는 도메인
어휘다. 라우팅·상태 관리·디자인 토큰·컴포넌트 프리미티브는 프론트엔드 개념이다.

`state-data`가 프로파일 역할인 것과 같은 판단이다. 데이터 레이어도 "화면 구현이 아닌
것"이지만 Capability로 올리지 않았다.

Capability로 올리려면 상수 목록을 프로파일이 주입하는 구조가 필요한데, 그러면 계약이
거의 비고 실질은 전부 프로파일에 있게 된다.

### 2. 수동 실행은 `workflowExtensions`에 넣지 않는 것으로 표현한다

`git-operations`는 `chaining.autoTriggerable: false`로 워크플로 자동 편입을 막는다.
프로파일 역할에는 그런 필드가 없다.

대신 **`workflowExtensions`에 삽입을 선언하지 않으면 그것이 곧 수동 전용**이다. 기능
흐름에 붙을 앵커가 없으므로 어느 워크플로에도 들어가지 않는다.

지금 프로파일 역할 셋(`design`·`accessibility`·`state-data`)은 전부 삽입돼 있다. 이
셋이 처음으로 삽입 없는 역할이 된다.

기능 요청이 프로젝트 골격을 다시 정하게 두면 안 되기 때문이다.

### 3. 변형이 아니라 역할 셋이다

`inspect`·`decide`·`scaffold`를 하나의 역할이 아니라 셋으로 나눈다.

프로파일 `agents[]`는 `additionalProperties: false`이고 `variants`를 선언할 수 없다.
그런데 세 단계는 **권한이 다르다.**

| 역할 | 도구 | 왜 |
|---|---|---|
| `project-design-inspect` | `Read` `Grep` `Glob` `Bash` (`readonly: true`) | 보는 일과 정하는 일을 섞으면 "이미 그랬다"와 "내가 정했다"가 구분되지 않는다 |
| `project-design-decide` | + `Write` `Edit` | 결정 문서만 쓴다 |
| `project-design-scaffold` | + `Write` `Edit` | 폴더·설정·규약 문서를 쓴다 |

하나로 합치면 `inspect`의 읽기 전용 보장이 사라진다. ADR-0007이 겪은 것과 같다 —
프롬프트에 "고치지 않는다"고 적는 것과 도구를 주지 않는 것은 다르다.

대신 **셋이 한 묶음이라는 관계가 계약에 선언되지 않는다.** 이름과 `roster` 배치와 각
역할 문서의 상호 참조로만 드러난다. 프로파일 역할에 변형 개념이 필요해지면 그때
스키마를 넓힌다.

### 4. `inspect`가 세 상태로 판정한다

| 판정 | 뜻 |
|---|---|
| 고정 | 코드와 문서가 일치하고 일관되게 지켜진다 |
| 암묵 | 코드에는 패턴이 있는데 어디에도 안 적혀 있다 |
| 없음 | 정해진 게 없다 |

**암묵이 가장 위험하다.** 다음 작업자가 모르고 다르게 하면 그때부터 두 패턴이
공존한다. `decide`는 암묵을 추인할지 바꿀지를 결정으로 남긴다.

이 판정 덕분에 greenfield와 기존 프로젝트가 **같은 진입점**을 쓴다. 새 프로젝트는
대부분 "없음"이 나오고, 기존 프로젝트는 "고정"과 "암묵"이 섞여 나온다.

### 5. 결정은 소비 저장소에 남긴다

`decide`의 산출물은 소비 저장소의 문서다. 이 하네스의 `docs/adr/`에 쓰지 않는다 —
그건 하네스 자신의 결정 기록이다.

다른 레이어와 권한 경계가 다르지 않다. `implementation`도 소비 저장소의 제품 코드를
쓴다. 하네스가 소비 저장소에서 실행될 때 "저장소"는 그쪽이다.

### 6. `DESIGN.md`가 비어 있으면 경고하고 통과한다

`design_ref` 슬롯의 기본값은 "DESIGN.md 표준 따름"이다. `DESIGN.md`가 비어 있으면 그
기본값이 가리킬 표준이 없다.

**차단하지 않는다.** 차단하면 새 프로젝트에서 첫 기능을 시작할 수 없다. 대신 경고에
`project-design-inspect`를 가리켜, 상수를 정하지 않은 채 진행 중이라는 사실이 드러나게
한다.

침묵 생략을 막는 이 저장소 방식과 결이 같다. 다만 여기서는 사유를 요구하는 대신 경고를
남긴다 — 상수 부재는 잘못이 아니라 아직 안 한 일이기 때문이다.

## 대가

**셋을 순서대로 부르는 것을 기계가 강제하지 않는다.** `scaffold`를 `decide` 없이
불러도 아무도 막지 않는다. 각 역할 문서가 선행을 요구하지만 프롬프트 수준이다.

Capability였다면 `requires`로 표현됐을 것이다. 프로파일 역할에는 그 수단이 없다.

**재실행 규칙이 없다.** 상수는 바뀐다. 상태 관리를 갈아엎을 때 이 셋을 다시 부르는지,
기능 작업으로 다루는지 정하지 않았다. `git-operations`에는 없는 문제다.

## 결과

- 프로젝트 상수를 정하는 자리가 생겼다. `DESIGN.md`를 채울 주체가 있다.
- 보는 일과 정하는 일과 만드는 일이 권한으로 갈린다.
- greenfield와 기존 저장소가 같은 진입점을 쓴다.
- 기능 흐름이 프로젝트 골격을 건드리지 않는다.

## 현재 강제 범위

검증기는 프로파일 역할의 도구가 권한 상한을 넘지 않는지 검사한다. `inspect`에 `Write`가
없으므로 파일을 쓸 수단이 없다.

다만 아래는 강제되지 않는다.

- **셋의 호출 순서.** `roster`는 이름 조회표일 뿐 순서를 담지 않는다.
- **`decide`가 소비 저장소에만 쓰는 것.** 하네스 파일을 고쳐도 검증기가 모른다.
  ADR-0005가 남긴 경로 단위 쓰기 금지 문제와 같다.
- **`DESIGN.md` 경고.** 완결성 게이트는 마크다운 문서이고 훅 런타임이 없다(ADR-0002).
  지금은 사람이나 메인 에이전트가 읽고 판단한다.
