# ADR-0007: 마지막 green 뒤의 역할은 코드를 고치지 않는다

- 상태: accepted
- 날짜: 2026-08-22
- 부분 대체: ADR-0005 결정 7 (앵커 이동의 근거)
- 관련 이슈: #22

## 배경

`accessibility`는 쓰기 도구를 갖고 "접근성 범위만 직접 고친다"고 선언돼 있었다. 그리고
모든 계층의 green이 끝난 뒤에 실행됐다.

```text
unit-green → ui-green → integration-green → e2e-green
  → accessibility   ← 여기서 코드를 고침
  → documentation
  → review          ← test.unit.result from unit-green 을 봄
```

판정 레이어가 보는 테스트 증거는 accessibility가 손대기 **전** 것이다. 그 사이에 바뀐
코드를 검증한 단계가 없다. 검증되지 않은 변경이 판정을 통과할 수 있었다.

선재 결함이다. ADR-0005 이전에도 앵커가 `review`였을 뿐 순서는 같았다.

## 결정

**마지막 green 뒤에 실행되는 역할은 코드를 고치지 않는다.** 발견한 것을 지적으로 내고
수정은 소유자에게 넘긴다.

`accessibility`에 적용한 결과다.

- 도구에서 `Write`·`Edit`를 제거하고 `readonly: true`를 선언한다
- 지적은 기존 `review-findings` 증거로 남긴다
- `routing`의 `키보드·포커스·ARIA·모션` 소유자를 `implementation`으로 바꾼다
- `roster`의 단위 이름을 `접근성·반응형 마감`에서 `접근성 점검·지적`으로 바꾼다

지적에는 **어떻게 고칠지**를 반드시 적는다. 구현자가 그것만 보고 고칠 수 있어야 한다.
"접근성 문제 있음"은 지적이 아니다.

### 왜 재검증 단계를 뒤에 붙이지 않았나

"accessibility 뒤에 테스트를 다시 돌린다"가 자연스러운 대안이지만 지금 구조로 안 된다.

프로파일의 `workflowExtensions[].insert[]`가 선언할 수 있는 것은 `id`·`runner`·`mode`·
`anchorCapability`·`anchorStep`·`background`·`isolation`·`note`가 전부다. `produces`도
`expect`도 없다. **프로파일은 증거를 내는 단계를 선언할 수 없다.**

core 워크플로에 넣는 것도 안 된다. `change.yaml`·`bugfix.yaml`·`review.yaml` 어디에도
`accessibility`가 없다. 코어는 이 역할의 존재를 모른다. "접근성 마감 뒤에 다시 돈다"를
코어가 알게 되면 ADR-0003의 경계와 프로파일이 스스로 적어 둔 규칙이 깨진다.

> 순서의 단일 출처는 core 워크플로다. 프로파일은 도메인 단계를 **어디에 끼울지**만 선언한다.

### 왜 증거 무효화를 도입하지 않았나

"쓰기 단계가 green 뒤에 오면 해당 계층 green을 무효화한다"가 더 일반적인 해법이다.
다만 무효화 개념이 통제 어휘에도, 워크플로 스키마에도, 게이트에도 없다. `produces`와
`expect`만으로는 "이 증거는 더 이상 유효하지 않다"를 표현할 수 없다.

지금은 마지막 green 뒤에 쓰기 권한을 가진 단계가 하나도 없으므로 무효화가 필요한 상황이
발생하지 않는다. 필요해지면 그때 설계한다.

## 선례

이 저장소가 판정 레이어에 같은 판단을 이미 내렸다.
`workflows/gates/require-test-evidence.md`가 그 이유를 적어뒀다.

> 하네스를 돌리려면 실행 권한이 필요하고, 실행 권한이 있으면 "잠깐 고쳐서 다시 돌려보는"
> 여지가 생긴다. 판정 레이어는 판정만 한다.

`accessibility`도 같은 자리에 있다. 판정 직전에서 코드를 고치면 그 수정을 검증할 단계가
뒤에 없다.

## review 전용 흐름

ADR-0005 결정 7이 앵커를 `review`에서 `documentation`으로 옮기면서, `review.yaml`에
`documentation` step이 없어 이 삽입이 건너뛰어지게 됐다.

**의도한 결과로 확정한다.** 판정만 하는 흐름에 코드를 감사하는 도메인 단계를 두지
않는다. 이 결정과 같은 방향이다.

## 대가

접근성 수정이 한 번 더 왕복한다. 전에는 `accessibility`가 발견과 수정을 한 번에 끝냈다.
이제는 `지적 → implementation → 해당 계층 red-green → 판정`이 된다.

느려지는 만큼 얻는 것은, 접근성 수정도 다른 모든 변경과 같은 검증을 받는다는 것이다.

## 결과

- 마지막 green 뒤에 코드를 고치는 단계가 없다. 판정 레이어가 보는 증거가 최신이다.
- 접근성 수정이 해당 계층의 red-green을 탄다.
- ADR-0005 결정 7의 앵커 이동은 유효하지만 근거가 바뀐다. 이제 `documentation` 앞에
  두는 이유는 "코드를 고치므로 문서보다 앞"이 아니라 "감사 결과를 문서와 판정이 함께
  본다"이다.

## 현재 강제 범위

검증기가 도구 목록과 Capability 권한을 대조한다. `accessibility`의 도구에서 `Write`와
`Edit`가 빠졌으므로 파일을 쓸 수단이 없다.

다만 **"쓰기 권한을 가진 단계를 마지막 green 뒤에 삽입하는 것" 자체는 막지 않는다.**
지금은 그런 단계가 없지만, 다른 프로파일이 같은 배치를 하면 같은 문제가 생긴다. 검증기
규칙으로 막는 것은 별건이며 #22에 선택지로 남아 있다.
