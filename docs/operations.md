# 운영 가이드

이 하네스를 **쓰는 법**과 **고치는 법**의 기준. 실제 작업 하나를 따라가는 예시는
`docs/walkthrough.md`, 구조 설명은 `README.md`, 결정 근거는 `docs/adr/`.

## 0. 먼저 알아야 할 것 — 지금 무엇이 자동인가

| 층 | 자동인가 | 어기면 |
|---|---|---|
| 선언 검사 (`npm run validate`) | **예** | 실패로 멈춤 |
| 미러 생성·드리프트 (CI) | **예** | 병합 차단 |
| 벤더링 드리프트 (`npm run vendor:check`) | **예** | 병합 차단 |
| 승인·금지 명령 (플랫폼 permission 설정) | **예.** Claude·Codex에 투영 | 확인을 묻거나 막힘 |
| 릴리스 버전 등급 (`version-advice`) | **아니오. 조언만** | PR에 추천이 붙고 판단은 사람이 한다 |
| 단계 브리핑 (`npm run step`) | **아니오. 보여주기만** | 안 봐도 아무 일도 안 일어난다 |
| 워크플로 순서·게이트 | 아니오 | 아무 일도 안 일어남 |
| 이관 게이트 (red 증거 요구 등) | 아니오 | 아무 일도 안 일어남 |
| 증거 기록 (`.harness/runs/`) | 아니오 | 기록이 안 남음 |
| 회귀 케이스 대조 (`tests/*.cases.yaml`) | 아니오 | 기준선이 조용히 내려감 |

**막는 것과 조언하는 것은 다르다.** `version-advice`는 절대 실패하지 않는다 — 무엇이
바뀌었는지까지만 확실히 하고 등급은 사람에게 넘긴다(ADR-0027).

**아래 절반은 사람이 지킨다.** 워크플로는 자동 파이프라인이 아니라 **대본**이고,
읽고 실행하는 건 사람 또는 메인 에이전트다. 실행 코드가 생기는 조건은
`docs/adr/0002-runtime-promotion.md`.

이 사실을 모르고 쓰면 "게이트가 있으니 알아서 막히겠지"라고 착각하게 된다. 안 막힌다.

## 1. 실행 — 작업을 시킬 때

### 1.1 워크플로 고르기

| 상황 | 워크플로 |
|---|---|
| 새 기능·변경 | `change` |
| 버그 수정 | `bugfix` |
| 이미 만든 것을 판정만 | `review` |

`change`와 `bugfix`는 계층별 red 게이트를 지킨다. `review`는 이미 만든 변경을 판정하는
예외라 red를 재현하지 않고 green 증거를 소비한다. `bugfix`도 red에서 예외가 아니다 — 재현 테스트가 먼저 실패해야
수정을 시작한다. 재현 없이 고치면 그 버그가 정말 사라졌는지도, 다시 돌아오지 않는지도
모른다.

### 1.2 순서대로 부르기

`/change`·`/bugfix`·`/review`가 이 절차의 진입점이다. 커맨드는 워크플로 파일을 가리킬
뿐 순서를 복제하지 않으므로, 아래 표와 어긋날 일이 없다. 다만 **증거 기록은 자동이
아니다** — 각 게이트가 볼 증거를 실제로 남겼는지 직접 확인한다.


`change` 기준이다. 각 단계에서 **다음으로 넘어가도 되는 조건**이 붙어 있다.

| # | 부르는 것 | 넘어가는 조건 |
|---|---|---|
| 0 | `commands.preflight` (있으면) | 0으로 끝나는가. 아니면 흐름 밖의 결함이다 |
| 1 | `discussion` | 필수 슬롯 7개가 다 찼는가 |
| 2 | `spec` | 계약이 **파일로** 나왔는가 (대화 속 서술은 계약이 아니다) |
| 3 | `tester#unit` | 순수 함수 입출력을 판정할 테스트가 있는가 |
| 4 | `test-runner#unit → implementation#logic → test-runner#unit` | unit red가 예상한 이유이고 이후 green인가 |
| 5 | `ui-scaffold → tester#ui → red → implementation#ui → green` | 실제 컴포넌트 단언으로 red/green을 닫았는가 |
| 6 | integration → e2e 계층별 red/green | 각 층이 독립적인 증거를 남겼는가 |
| 7 | `documentation` | 2번의 문서 영향 판정이 지목한 문서를 다 고쳤는가 |
| 8 | `review` | 6·7번 증거가 다 있는가 |
| — | `project-design-inspect` → `decide` → `scaffold` | **사람이 명시적으로.** 프로젝트당 한 번 |
| — | `commit` · `push` · `pr-create` | **사람이 명시적으로** |

**이 표에 없는 단계가 있다.** 프로파일이 `workflowExtensions`로 도메인 단계를 끼운다.
그 목록은 여기 적지 않는다 — 프로파일이 소유하고 프로파일마다 다르다. 생성된 커맨드
(`.claude/commands/<workflow>.md`)가 무엇이 몇 개 붙는지 알려주고, 어디에 붙는지는
`profiles/<id>/profile.yaml`에서 읽는다. 워크플로 파일과 이 표만 따르면 도메인 단계가
통째로 빠지고, 아무것도 그것을 지적하지 않는다.

0단계는 소비 저장소가 `commands.preflight`를 선언했을 때만 있다. 툴체인 같은 흐름 밖
선행조건을 저장소가 스스로 검사하는 자리다 — 실패하면 되돌릴 곳이 흐름 안에 없으므로
사람이 고치고 다시 시작한다 (ADR-0026).

1단계를 건너뛰어도 된다. 요구사항이 이미 명확하면 `discussion` 없이 2번부터 시작한다.
다만 어떤 동작 구현도 같은 계층 red와 분리할 수 없다. 그게 이 공정의 핵심이다.

### 1.3 각 게이트에서 실제로 볼 것

**2번 — 계약이 고정됐나**

- 타입·props가 파일에 있는가
- 데이터 접근 훅 **시그니처**가 있는가 (실제 훅이 아니라 시그니처)
- test-id 규약이 있는가
- **문서 영향 판정(`documentation-impact`)이 있는가.** `required`면 영향받는 문서가
  경로로 나열돼 있는가
- "TBD"·"나중에"가 남아 있지 않은가

하나라도 없으면 하류가 추측하게 된다. 되돌린다.

**3번 — 인수 기준이 빠짐없이 테스트로 내려왔나**

테스트는 `specification.test-plan`이 지정한 계층으로 분담합니다. unit은 순수 함수,
ui는 단일 실제 컴포넌트, integration은 여러 모듈 경계, e2e는 사용자 여정을 검증합니다.
각 계층 요약의 **인수 기준 ↔ 테스트 대응표**를 봅니다. 빠진 기준이 있으면 그 기준은
구현 전에 실패해 볼 기회를 잃습니다.

구현자는 인수 기준 검증 테스트를 쓰지 않습니다. 코드를 쓴 뒤에 쓰는 테스트는 요구사항이
아니라 구현을 확인하는 것이라 통과하는 테스트를 쓰게 됩니다.

**4번 — red가 진짜 red인가**

| 실패 이유 | 판정 |
|---|---|
| 단언 실패, 기대값 불일치, 미구현 반환 | ✅ 진행 |
| 컴파일·타입 에러 | ❌ `tester`로 되돌림 |
| import·모듈 해석 실패 | ❌ `tester`로 되돌림 |
| 픽스처·설정 누락 | ❌ `tester`로 되돌림 |
| UI/E2E가 화면·서버 부재로 못 뜸 | ❌ red 아님. 선행 스캐폴드·green 단계로 되돌림 |

"빨갛다"와 "올바른 이유로 빨갛다"는 다르다. 후자만 구현 착수 근거다.

**6번 — 층을 합치지 않았나**

unit은 생략 불가다. UI가 없으면 테스트 계획의 구체적 사유로 UI 체인을 생략할 수 있다.
integration·e2e를 생략하려면 **사유와 승인**이 있어야 한다.
"이번엔 필요 없어서"는 사유가 아니다. "이 변경은 순수 함수만 건드리고 UI 경로가 없음"이
사유다.

**7번 — 문서 갱신이 판정 범위를 지켰나**

| `documentation-impact` | 통과 조건 |
|---|---|
| 없음 | 차단. 2번으로 되돌린다 |
| `required` | 판정이 지목한 문서가 전부 changeset에 있는가 |
| `not-applicable` | 구체적인 생략 사유가 기록됐는가 |

**부분 갱신도 차단이다.** A·B를 지목했는데 A만 고쳤으면 B가 조용히 낡는다. B를 이번에
고치지 않기로 했다면 그것도 사유가 필요하다.

판정은 `spec`이 하고 실행은 `documentation`이 하고 대조는 게이트가 한다. 세 주체가
다르기 때문에 생략이 검증 가능해진다 — 실행 주체가 자기 일의 유무를 스스로 정하면
생략은 항상 정당해 보인다.

**8번 — review가 테스트를 돌리고 있지 않나**

`review`는 판정만 한다. 증거가 없으면 판정하지 말고 해당 증거를 만드는 단계로
되돌린다. 판정 축이 둘이라 게이트도 둘이다.

### 1.4 실패했을 때 어디로 되돌리나

| 증상 | 되돌릴 곳 |
|---|---|
| 요구사항 슬롯 부족·수용 기준 모호 | `discussion` |
| 프로젝트 상수 부재·암묵 규약 충돌 | `project-design-decide` |
| 계약 드리프트·타입 불일치 | `spec` |
| 토큰 부재·대비 부족 | `design` |
| 테스트가 돌지 않음·red rejected | `tester` |
| 마크업·렌더 상태 | `implementation` |
| 데이터 페칭·상태 로직 | `state-data` |
| 커버리지 누락 | `tester` |
| 문서 누락·설명과 계약 불일치 | `documentation` |
| 문서 영향 판정이 없음 | `spec` |
| 키보드·포커스·ARIA | `implementation` (발견은 `accessibility`) |

이 표의 단일 출처는 `profiles/frontend/profile.yaml`의 `routing`이다.

**재시도는 1회까지.** 같은 브리프로 두 번 실패하면 브리프를 보강하거나 상위로 올린다.
정책 거부(`policy-denied`)는 재시도 대상이 아니다 — 다시 해도 같은 이유로 거부된다.

### 1.4.1 되돌린다는 것이 무엇인가

`capability.yaml`의 `failure.<유형>.action`은 **실행 지시가 아니다.** 흐름을 되감는
주체가 없으므로(`ADR-0002`), 되돌림은 사람 또는 메인 에이전트가 목적지 단계를 다시
부르고 그 뒤부터 다시 진행하는 것이다. `action`은 **어디로 갈지를 지목**할 뿐이다.

| 상황 | 어떻게 |
|---|---|
| 목적지가 이 흐름 안에 있다 | 그 단계부터 다시 진행한다 |
| 목적지가 `assumes`에 있다 | 흐름 밖 선행조건 결함이다. 사람이 채우고 흐름을 다시 시작한다 |
| 목적지에 권한이 없다 | 되돌릴 곳이 틀린 것이다. 라우팅이나 워크플로 구조를 고친다 |

**재개 규칙은 하나다.** 다시 실행한 단계의 산출에 **의존하는 하류 증거는 무효**다.
지우지 않고 남기되 새 증거가 그 위에 쌓인다. 의존하지 않는 계층까지 다시 돌리지 않는다.

계약이 모호해서 멈춘 경우는 실패가 아니다 — 되돌리거나, 되돌리지 않기로 하고
`contract-deviation`과 승인을 남긴다. 기록만으로는 진행할 수 없다
(`capabilities/specification/hooks/contract-freeze.md`).

### 1.4.2 증거를 어디에 쓰나

**격리 안에서 쓰지 않는다.** 격리된 역할(`isolation: worktree`)은 산출을 반환하고,
증거는 **그것을 부른 쪽이 주 체크아웃에** 남긴다. 격리 안에 쓰면 worktree 정리와 함께
사라진다 — 실제로 증거 파일 하나가 그렇게 소실됐다 (ADR-0018).

`.harness/`는 커밋하지 않는다. 실행마다 달라지는 산출물이라 저장소가 오염되고, 관측된
소실은 커밋 여부와 무관했다. **대가는 증거가 한 머신에 갇히는 것이다** — 다른 기기·CI·
다른 실행자는 못 본다.

이 규칙을 강제하는 것은 없다. 어디에 쓰느냐는 실행 시점의 일이라 선언 검사가 닿지 않는다.

### 1.4.3 끊긴 흐름을 이어받을 때

세션이 끊겨도 **같은 `runId`를 이어 쓴다.** 새로 만들면 증거가 두 디렉터리로 갈라지고,
게이트가 보려는 증거는 앞쪽에 있는데 지금 실행은 뒤쪽을 본다 — 그러면 처음부터 다시
하거나, 봤다고 착각하고 통과시킨다 (ADR-0022).

**이미 기록된 증거는 다시 만들지 않는다.** 게이트는 증거를 보지 그 증거가 어느 세션에서
나왔는지 묻지 않는다. 무효가 되는 것은 세션이 끊긴 것이 아니라 **다시 실행한 단계의
산출에 의존하는 하류 증거**다 (§1.4.1).

다음 세션이 `runId`를 아는 방법은 지금 **사람이 알려주는 것**뿐이다. 포인터를 둘 주체가
없다.

### 1.3.1 단계 하나를 시작할 때

```bash
npm run step <workflow> <step>     # 또는 /step
```

게이트·선행 증거·남길 증거·내는 토큰·프로파일 삽입을 한 화면에 모은다. 워크플로·
capability·프로파일·게이트를 **호출 시점에** 읽으므로 내용이 낡지 않는다(ADR-0032).
어휘는 읽지 않는다 — 토큰 이름만 나오고 뜻은 `docs/vocabulary.md`에 있다.

**보여주기만 한다.** 단계를 부르지도 증거를 남기지도 않는다.

### 1.4.4 두 흐름을 동시에 돌리지 않는다

**한 체크아웃에서 활성 `runId`는 하나다**(ADR-0028). 흐름 하나가 끝나거나 버려진 뒤에
다음을 시작한다.

이 문장이 §1.4.3의 "이어받기"와 동시 실행을 가른다 — 이어받기는 이전 흐름이 **아직
안 끝난** 것이고, 동시 실행은 활성인 것이 **둘**이다.

두 흐름이 한 트리를 공유하면 제품 코드가 섞이고, 흐름마다 체크아웃을 주면 증거를 남길
"주 체크아웃"이 둘이 되어 §1.4.2가 성립하지 않는다.

**흐름 안의 병렬은 다르다.** `background: true`인 역할은 부른 쪽과 나란히 돌고, 쓰는
역할이면 `isolation: worktree`로 갈라진다. 그 짝은 검증기가 본다.

이 규칙을 강제하는 것은 없다. 두 흐름을 동시에 시작해도 아무것도 안 막는다.

### 1.5 실패를 하네스에 적립한다

§1.4는 **그 실행**을 구제한다. 이 절은 **다음 실행**을 구제한다. 되돌려서 통과시키고 끝내면
같은 실패가 다음에 또 나고, 그때 알아채는 사람이 없으면 아무 일도 일어나지 않는다. 실패가
그 실행의 재시도로만 소비되면 하네스는 그대로다.

실패 하나마다 질문 하나를 더 던진다.

> **이 실패를 막을 수 있었던 통제가 하네스에 있었는가?**

답은 셋 중 하나다.

| 답 | 무엇을 하나 |
|---|---|
| 있었는데 안 걸렸다 | 통제가 왜 통과시켰는지 본다. 게이트·검증기·훅의 결함이다. 고치고 그 케이스를 적립한다 |
| 없었다. 만들 수 있다 | §2로 간다. 검증기 규칙·게이트·정책 중 어디에 넣을지 정하고, 만든 뒤 케이스를 적립한다 |
| 없었다. 만들 수 없다 | 내용 판단의 영역이다. §2.4의 "안 막아준다" 목록에 있는지 본다. 없으면 그 목록에 추가한다 |

#### 통제 유형마다 적립 위치가 다르다

| 통제 | 케이스를 어디에 | 러너 |
|---|---|---|
| 검증기 규칙 | `tooling/validators/contracts.test.mjs` | ✅ `npm run test:contracts` — CI가 돈다 |
| 게이트·훅 | `capabilities/<id>/tests/*.cases.yaml` | 없음. 사람이 대조한다 (§2.5) |
| 정책 | 강제 수단을 따라간다. 검증기면 첫 행, 훅이면 둘째 행 | `policies/README.md`의 ✅/⏳ |

**검증기 쪽만 기계가 지킨다.** 그래서 통제를 검증기 규칙으로 만들 수 있으면 그쪽이 낫다.

다만 `validate.mjs` 안에 인라인으로 쓴 검사에는 케이스를 붙일 수 없다.
`contracts.test.mjs`가 부르는 것은 순수 헬퍼(`workflow-graph`·`profile-roster`·
`profile-testing`·`documentation-gate`·`commands`)뿐이다. **회귀로 고정하려면 검사를 순수
함수로 먼저 빼낸다.** 인라인으로 두면 통제는 있어도 그 통제의 회귀는 없다.

**적립하지 않기로 하는 것도 판단이다.** 빈칸으로 두지 말고 셋째 답임을 사유와 함께 남긴다.
빈칸과 "통제로 만들 수 없다고 판단함"은 다르다. 앞의 것은 아무도 생각하지 않았다는 뜻이고
뒤의 것은 생각한 결과다.

**같은 실패가 두 번 나면 적립은 선택이 아니다.** `ADR-0002`가 실행 코드 승격 신호로 적어
둔 것과 같은 문장이다.

> 승격을 결정하는 신호는 "코드가 있으면 멋있다"가 아니라 **"프롬프트로는 지켜지지 않는
> 규칙이 반복해서 깨진다"** 이다.

#### 어디에 적립하나

이 저장소는 **이슈**를 적립 지점으로 쓴다. 실패를 이슈로 남길 때 본문에 절을 하나 고정한다.

```markdown
## 드러난 통제 부재

- 막을 수 있었던 통제: <있었는데 안 걸림 | 없음, 만들 수 있음 | 없음, 만들 수 없음>
- 적립할 곳: <검증기 규칙 | 게이트 | 정책 | 회귀 케이스 | 없음(사유)>
```

`docs/adr/`가 결정을 남기는 것과 같은 이유다. 판단이 문서에 남지 않으면 판단한 사람에게만
남고, 그 사람이 바뀌면 사라진다.

#### 지금의 한계

**"두 번 났다"를 셀 수단이 없다.** `failure.classified` 이벤트를 내는 주체가 없어서
(`packages/telemetry-contracts/`) 무엇이 몇 번 깨졌는지는 사람이 기억하는 범위에서만 안다.
이 절은 그 한계 위에서 도는 절차다.

## 2. 관리 — 하네스를 고칠 때

### 2.1 무엇을 고치면 무엇을 돌리나

| 고치고 싶은 것 | 어디를 | 그 다음 |
|---|---|---|
| 이관 조건 (앞 단계 증거 요구) | `workflows/gates/` + step의 `gate:` | `npm run check` |
| 역할이 하는 일 | `capabilities/<id>/agents/*.md` | `npm run check` |
| 도구·모델·권한 | `capabilities/<id>/capability.yaml` | `npm run check` |
| 선행조건·산출물·증거 | 같은 파일 | `npm run check` |
| 도메인 지식 (토큰·규칙) | `profiles/<id>/` | `npm run check` |
| 삽입 단계의 증거·생략 조건 | `profiles/<id>/profile.yaml`의 `workflowExtensions[].insert[]` | `npm run check` |
| 실행자 이름·단계 구성 | `profiles/<id>/profile.yaml` | `npm run check` |
| 작업 순서 | `workflows/*.yaml` | `npm run check` |
| 금지 규칙 | `policies/` | `npm run check` |
| 검증기 규칙 | `tooling/validators/` + `policy-enforcement.mjs` 레지스트리 | `npm run check` |
| 게이트·훅의 회귀 케이스 | `capabilities/<id>/tests/*.cases.yaml` | 사람이 대조 (러너 없음) |
| 새 토큰 | `docs/vocabulary.md` **+** `vocabulary.json` | `npm run check` |
| 승인의 명령 패턴 | `tooling/generators/permissions.json` | `npm run generate` |
| 플랫폼 모델 이름 | `tooling/generators/platforms.json` | `npm run generate` |
| 벤더링 팩을 새로 받음 | `profiles/<id>/skills/<pack>/` | `npm run vendor:record` **+** 그 diff를 리뷰 |

**새 검증기 규칙은 순수 함수로 쓴다.** `validate.mjs`에 인라인으로 쓰면
`contracts.test.mjs`가 닿지 못해 **그 통제의 회귀가 없다** — 통제는 있는데 그것이 나중에
느슨해지는 것을 잡을 케이스가 없다. 판정은 순수 모듈에 두고 `validate.mjs`는 부르고
보고만 한다. 정책이 강제 수단으로 지정하는 규칙이면 `policy-enforcement.mjs`의
레지스트리에도 등록한다.

**`.claude`·`.codex`는 절대 직접 고치지 않는다.** 고쳐도 다음 생성 때
되돌아가고, CI가 병합을 막는다.

### 2.2 어디에 넣을지 판단하는 기준

새로 무언가를 추가할 때 **딱 하나만 물으면 된다.**

> 프론트엔드가 아닌 프로젝트에서도 이게 필요한가?

| 답 | 위치 |
|---|---|
| 예 | `capabilities/` |
| 아니오 | `profiles/frontend/` |

React 규칙 → 아니오 → 프로파일. 테스트 실행 → 예 → Capability.
디자인 토큰 → 아니오 → 프로파일. 계약 고정 → 예 → Capability.

판단이 애매하면 **프로파일에 넣는다.** 나중에 Capability로 올리는 건 쉽고,
Capability에서 도메인 지식을 빼내는 건 어렵다.

### 2.3 Capability 하나 추가하는 절차

```sh
mkdir -p capabilities/<id>/{agents,hooks,tests}
```

1. `capability.yaml`을 쓴다. `id`는 디렉터리명과 같아야 한다.
2. `requires`/`produces`에 쓸 토큰이 `docs/vocabulary.md`에 있는지 본다.
   없으면 → 코어에 필요한가? 아니면 프로파일 네임스페이스(`<ns>:`)로.
3. **증거를 정한다.** 증거 없이 완료되는 Capability는 만들지 않는다.
   다음 단계가 상태가 아니라 증거로 넘어오기 때문이다.
4. `agents/*.md`에 본문을 쓴다. **frontmatter를 넣지 않는다** — 메타데이터는
   manifest가 소유하고, 남아 있으면 생성기가 오류로 잡는다.
5. 훅이나 게이트를 둔다면 `tests/<이름>.cases.yaml`에 그 동작이 반드시 이래야 하는
   케이스를 쓴다. 러너는 없지만(ADR-0002) 이 파일이 회귀 목록이 된다 — 훅을 고칠 때
   같은 판정이 나오는지 사람이 대조한다. 겪은 실패가 있으면 그것부터 케이스로 넣는다.
6. `npm run check`.

중앙 registry도, 오케스트레이터도 고치지 않는다. 그게 이 구조의 목적이다.

### 2.4 검증기가 막아주는 것 / 안 막아주는 것

**막아준다** (틀리면 즉시 실패)

- 어휘 오타, 없는 파일 참조, 권한 초과, 프로파일의 권한 확대
- `readonly` 역할이 쓰기 도구를 드는 것, 정책이 지정한 검증기가 실재하지 않는 것
- 코어 증거가 `artifactRequired` 없이 선언되는 것 (경로 없는 증거는 세션과 함께 사라진다)
- `moot`을 허용하는 계층에서 그 분기를 지우는 것 (ADR-0012가 연 경로가 조용히 닫힌다)
- 스캐폴드 단계를 지우거나 red 게이트 뒤로 미는 것 (ADR-0011이 푼 교착이 되살아난다)
- 어휘가 연 수동 검증 경로를 선언이 안 내놓는 것, `manual` 계층에 러너 명령이 함께 있는 것
- 선행 토큰의 생산자가 흐름 안에도 `assumes`에도 없는 것 (되돌려도 갈 곳이 없다)
- 흐름이 스스로 생산하거나 아무도 요구하지 않는 `assumes`가 남아 있는 것
- 벤더링한 파일이 기록된 해시와 달라지는 것, 마커만 지워 대조를 피하는 것
- `npm run check`에 넣은 검사가 CI 목록에 없는 것 (로컬에서만 돌고 병합을 못 막는다)
- 삽입 단계가 증거·완료 조건 없이 선언되는 것, 그 증거가 미등록 토큰인 것
- 소비 저장소를 하네스 안에 중첩하는 것 (격리가 아무것도 격리하지 못한다)
- 프로파일이 코어 밖 호스트를 allowlist에 더하는 것, repository 프로파일의 빈 allowlist
- 아무도 부르지 않는 명령 키 (오타이거나 죽은 명령 — ADR-0026)
- 승인을 요구하는 변형이 플랫폼별로 투영되지 않는 것, 투영도 사유도 없는 플랫폼 (생성 실패)
- 테스트 층 합치기, Git 작업 자동화, 파괴적 작업 자동 진행
- 오케스트레이터에 도메인 지식 유입, 미러 드리프트
- 문서 단계 없이 판정으로 가는 워크플로, roster·routing의 없는 실행자 이름
- 프로파일이 같은 단계를 한 워크플로에 두 번 삽입하는 것

**안 막아준다** (사람이 봐야 함)

- 역할 본문이 실제로 말이 되는지
- 워크플로 순서가 이 조직에 맞는지
- 증거를 정말 남겼는지, 선언한 `artifact` 경로에 파일이 실제로 생겼는지 (기록 주체가 없다)
- 증거를 격리 밖에 썼는지 (§1.4.2)
- 자동화가 못 잡는 관측성 문제 (그룹핑·재현 컨텍스트·샘플링) — 볼 역할이 없다 (ADR-0019)
- `preflight`를 실제로 돌렸는지 (규약이지 장치가 아니다 — ADR-0026)
- `measurement`가 수용 기준과 섞였는지 (출시 뒤에 답이 나오는 지표여야 한다 — ADR-0021)
- 역할이 자기 경로 범위 안에만 썼는지 (경로는 프롬프트에만 있다 — ADR-0024)
- 끊긴 흐름이 같은 `runId`를 이어 쓰는지 (규약이지 장치가 아니다 — ADR-0022)
- 벤더링한 내용이 **상류와** 같은지 (기록 대조는 로컬 변조만 본다 — ADR-0016)
- 두 흐름을 동시에 돌렸는지 (규약이지 장치가 아니다 — ADR-0028 · §1.4.4)
- 역할이 `Bash`로 파일을 썼는지 (도구 표가 `Bash`를 read로 분류한다 — 격리 검사도 권한 등급 대조도 못 본다)
- 재시도가 선언한 `maxAttempts`를 지켰는지 (숫자는 있고 세는 주체가 없다 — ADR-0029)
- 쓰기·토큰이 얼마나 쓰였는지 (축이 없다. 플랫폼 권한에 수량이 없어 투영할 곳도 없다 — ADR-0029)
- 신뢰성이 실제로 얼마인지 (차원은 계약에 있고 집계는 하네스 밖이다. Adapter가 아직 없다 — ADR-0031)
- 훅이 요구하는 검사를 실제로 했는지
- 문서 영향 판정이 맞는지, 생략 사유가 진짜 사유인지

즉 **"구조가 일관적인가"는 자동, "내용이 옳은가"는 수동**이다.

### 2.5 회귀 적립 현황

`policies/README.md`가 정책의 ✅/⏳ 를 표로 드러내는 것과 같은 이유로 둔다. **래칫이 돌지
않을 때 돌지 않는다는 것이 보여야 한다.** 표가 없으면 회귀 목록이 둘뿐인 상태와 여덟인
상태가 똑같아 보인다.

#### 통제 유형별

§1.5가 통제 유형마다 적립 위치를 나눈다. 현황도 같은 축으로 본다. **한쪽만 보면 오독한다** —
검증기 쪽에 적립하고 게이트 쪽에 아무것도 안 넣은 사이클은 아래 세부 표만 보면 래칫이 안 돈
것처럼 보인다.

| 통제 | 어디에 | 러너 | 현황 |
|---|---|---|---|
| 검증기 규칙 | `tooling/validators/contracts.test.mjs` | ✅ CI가 돈다 | `npm run test:contracts`가 수를 낸다 |
| 게이트·훅 | `capabilities/<id>/tests/*.cases.yaml` | 없음. 사람이 대조 | 아래 세부 표 |
| 정책 훅 | — | ⏳ 훅 런타임 (`ADR-0002`) | 적립할 자리가 아직 없다 |

**수를 여기 적지 않는다.** 매 PR마다 바뀌는 값을 손으로 옮기면 낡는다. `policies/README.md`의
✅/⏳ 표가 실제로 그렇게 어긋나 있었고 — `blocking-hooks-preserved`가 ⏳ 로 적혀 있는 동안
정적 검사가 이미 일부 돌고 있었다 — 그래서 그 표의 단일 출처를 레지스트리로 옮겼다. 여기서도
같은 판단을 한다. **바뀌지 않는 것(위치·러너 유무)만 적고, 변하는 수는 명령이 답한다.**

#### 게이트·훅 세부

러너가 없는 쪽이라 사람이 대조한다. 무엇이 대조 대상인지가 여기 있다.

| Capability | 회귀 케이스 | 품질 평가 |
|---|---|---|
| `requirements` | ✅ `tests/completeness-gate.cases.yaml` | ✅ `evals/slot-extraction.eval.yaml` |
| `specification` | ✅ `tests/contract-freeze.cases.yaml` | ✅ `evals/contract-quality.eval.yaml` |
| `test-design` | 없음 | 없음 |
| `test-execution` | 없음 | 없음 |
| `implementation` | 없음 | 없음 |
| `documentation` | 없음 | 없음 |
| `review` | 없음 | 없음 |
| `git-operations` | 없음 | 없음 |

**빈칸을 미리 채우지 않는다.** 통제는 실패에서 나온다. 겪지 않은 실패의 케이스를 상상해서
쓰면 무엇을 막는지 모르는 목록이 된다. §1.5가 도는 만큼 이 표가 채워진다. **실패를 겪고도
안 채워지면 래칫이 안 돌고 있다는 뜻이다** — 표가 그대로인 것 자체는 실패가 없었다는
뜻일 수도 있으므로 둘을 가른다.

두 가지가 아직 이 표 뒤에 있다.

- **러너가 없다.** 대조는 사람이 한다 (`test-kit`). 승격 순서에서 마지막이었는데
  ADR-0023이 3번으로 올렸다 — 래칫이 도는지 확인하는 수단이 마지막에 있을 이유가 없다.
- **이 파일들은 어떤 manifest에도 선언돼 있지 않다.** `capability.yaml`의 `entrypoints`는
  `agents`·`skills`·`tools`·`hooks`만 받는다. 지워도 검증기가 잡지 못한다.

### 2.6 정기 점검

```sh
npm run check          # 선언 + 드리프트
git status             # 미러가 손으로 고쳐지지 않았는지
```

주기적으로 볼 것:

- 그 사이 실패가 있었다면 §1.5대로 기록됐는가 → §2.5가 그대로인 이유가 무실패인지 미실행인지 가른다
- §2.5는 두 표를 함께 본다 → 세부 표만 보면 검증기 쪽 적립이 안 보인다
- `policies/README.md`의 ⏳ 항목이 아직도 강제되지 않는가 → ADR-0002 조건 재검토
- `docs/vocabulary.md`에 아무도 안 쓰는 토큰이 쌓이지 않았는가
- 에이전트 `description`이 길어지지 않았는가 (세션마다 로드되는 유일한 부분)
- `profiles/`가 하나뿐인가 → 하나면 "도메인 무관"은 아직 검증되지 않은 주장이다

### 2.7 릴리스 — 언제 끊고 무엇을 올리나

**축은 `package.json` 하나다**(ADR-0027). 파일마다 개정 번호를 두지 않는다.

**CHANGELOG를 두지 않는다.** git 이력과 ADR이 이미 무엇이 왜 바뀌었는지 적고 있고,
세 번째 사본은 낡는다. 릴리스 노트는 GitHub Release에 쓴다 — 태그가 커밋을 가리키므로
갈릴 자리가 없다.

#### 언제

공개 표면이 바뀌었고 그것이 **한 덩어리로 말이 될 때.** PR마다 `version-advice`가
무엇이 바뀌었는지 적어 주지만 등급은 정하지 않는다 — 기계가 못 정한다.

공개 표면이 무엇인지는 `.github/scripts/version-advice.mjs`의 `SURFACE`가 갖고 있다.
여기 옮겨 적지 않는다.

#### 등급

**등급 기준과 `0.x` 규칙은 `.github/copilot-instructions.md`가 갖고 있다.** 여기 옮겨
적지 않는다 — 리뷰어가 읽는 파일이 그것이고, 두 곳에 적으면 한 곳이 낡는다.

#### 어떻게

**별도 `chore:` PR로 끊는다. 기능 PR에 섞지 않는다.**

릴리스는 "무엇을 만들었나"와 다른 판단이다 — 지금까지 쌓인 것이 한 덩어리인지를
본다. 기능 PR에 얹으면 그 판단이 PR 수만큼 늘고, 각각은 자기 변경만 본다.

```bash
npm version <major|minor|patch> --no-git-tag-version   # PR에서. 태그는 아직 안 단다
# ── 머지 후 ──
git tag -a v<버전> -m "v<버전> — <한 덩어리를 한 줄로>"
git push origin v<버전>
gh release create v<버전> --title "v<버전> — <같은 한 줄>" --notes "<무엇을 끊었나>"
```

`--no-git-tag-version`을 빼면 `npm version`이 그 자리에서 태그를 단다. **태그는 머지된
커밋에 달아야 하므로** PR 안에서 달면 사라질 커밋을 가리킨다.

주석 태그(`-a`)를 쓴다. 단순 태그는 메시지도 날짜도 남기지 않는다.

## 3. 자주 하는 실수

| 실수 | 왜 문제인가 |
|---|---|
| 미러를 직접 고침 | 다음 생성에 사라짐. CI가 막음 |
| 본문 md에 frontmatter를 넣음 | manifest와 갈라짐. 생성기가 오류 |
| Capability에 프레임워크 이름을 씀 | 프로파일 교체해도 도메인이 따라옴 |
| 증거 없이 다음 단계로 감 | 무엇이 왜 통과했는지 사후에 알 수 없음 |
| 컴파일 에러를 red로 침 | 초록이 됐을 때 요구사항 만족인지 에러 소멸인지 구분 불가 |
| 커밋 후 자동으로 푸시 | 되돌리기 어려운 작업을 의도하지 않은 시점에 실행 |
| 어휘 파일을 한쪽만 고침 | 사람이 읽는 것과 기계가 읽는 것이 갈라짐 |
| 벤더링 파일에 lint --fix를 돌림 | 상류 변경과 우리 수정이 구분되지 않음. 실제로 났다 |
| 워크플로 파일만 읽고 진행함 | 프로파일이 끼운 도메인 단계가 조용히 빠짐 |
| 수동으로 확인하고 생략으로 기록함 | 검증한 것과 안 한 것이 같은 토큰이 되고 승인만 남발됨 |
| 계약이 모호한데 추측으로 진행함 | 이후 계층이 검증 안 된 가정 위에 서고, 판정 때는 되돌리기에 비쌈 |
