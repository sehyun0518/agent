# 운영 가이드

이 하네스를 **쓰는 법**과 **고치는 법**의 기준. 실제 작업 하나를 따라가는 예시는
`docs/walkthrough.md`, 구조 설명은 `README.md`, 결정 근거는 `docs/adr/`.

## 0. 먼저 알아야 할 것 — 지금 무엇이 자동인가

| 층 | 자동인가 | 어기면 |
|---|---|---|
| 선언 검사 (`npm run validate`) | **예** | 실패로 멈춤 |
| 미러 생성·드리프트 (CI) | **예** | 병합 차단 |
| 워크플로 순서·게이트 | 아니오 | 아무 일도 안 일어남 |
| 이관 게이트 (red 증거 요구 등) | 아니오 | 아무 일도 안 일어남 |
| 증거 기록 (`.harness/runs/`) | 아니오 | 기록이 안 남음 |

**아래 절반은 사람이 지킨다.** 워크플로는 자동 파이프라인이 아니라 **대본**이고,
읽고 실행하는 건 사람 또는 메인 에이전트다. 실행 코드가 생기는 조건은
`docs/adr/0002-runtime-promotion.md`.

이 사실을 모르고 쓰면 "게이트가 있으니 알아서 막히겠지"라고 착각하게 된다. 안 막힌다.

## 1. 실행 — 작업을 시킬 때

### 1.1 워크플로 고르기

| 상황 | 워크플로 |
|---|---|
| 새 기능·변경 | `change` |
| 버그 수정 | `bugfix` |
| 이미 만든 것을 판정만 | `review` |

`change`와 `bugfix`는 계층별 red 게이트를 지킨다. `review`는 이미 만든 변경을 판정하는
예외라 red를 재현하지 않고 green 증거를 소비한다. `bugfix`도 red에서 예외가 아니다 — 재현 테스트가 먼저 실패해야
수정을 시작한다. 재현 없이 고치면 그 버그가 정말 사라졌는지도, 다시 돌아오지 않는지도
모른다.

### 1.2 순서대로 부르기

`change` 기준이다. 각 단계에서 **다음으로 넘어가도 되는 조건**이 붙어 있다.

| # | 부르는 것 | 넘어가는 조건 |
|---|---|---|
| 1 | `discussion` | 필수 슬롯 6개가 다 찼는가 |
| 2 | `spec` | 계약이 **파일로** 나왔는가 (대화 속 서술은 계약이 아니다) |
| 3 | `tester#unit` | 순수 함수 입출력을 판정할 테스트가 있는가 |
| 4 | `test-runner#unit → implementation#logic → test-runner#unit` | unit red가 예상한 이유이고 이후 green인가 |
| 5 | `ui-scaffold → tester#ui → red → implementation#ui → green` | 실제 컴포넌트 단언으로 red/green을 닫았는가 |
| 6 | integration → e2e 계층별 red/green | 각 층이 독립적인 증거를 남겼는가 |
| 7 | `review` | 6번 증거가 다 있는가 |
| — | `commit` · `push` · `pr-create` | **사람이 명시적으로** |

1단계를 건너뛰어도 된다. 요구사항이 이미 명확하면 `discussion` 없이 2번부터 시작한다.
다만 어떤 동작 구현도 같은 계층 red와 분리할 수 없다. 그게 이 공정의 핵심이다.

### 1.3 각 게이트에서 실제로 볼 것

**2번 — 계약이 고정됐나**

- 타입·props가 파일에 있는가
- 데이터 접근 훅 **시그니처**가 있는가 (실제 훅이 아니라 시그니처)
- test-id 규약이 있는가
- "TBD"·"나중에"가 남아 있지 않은가

하나라도 없으면 하류가 추측하게 된다. 되돌린다.

**3번 — 인수 기준이 빠짐없이 테스트로 내려왔나**

테스트는 `specification.test-plan`이 지정한 계층으로 분담합니다. unit은 순수 함수,
ui는 단일 실제 컴포넌트, integration은 여러 모듈 경계, e2e는 사용자 여정을 검증합니다.
각 계층 요약의 **인수 기준 ↔ 테스트 대응표**를 봅니다. 빠진 기준이 있으면 그 기준은
구현 전에 실패해 볼 기회를 잃습니다.

구현자는 인수 기준 검증 테스트를 쓰지 않습니다. 코드를 쓴 뒤에 쓰는 테스트는 요구사항이
아니라 구현을 확인하는 것이라 통과하는 테스트를 쓰게 됩니다.

**4번 — red가 진짜 red인가**

| 실패 이유 | 판정 |
|---|---|
| 단언 실패, 기대값 불일치, 미구현 반환 | ✅ 진행 |
| 컴파일·타입 에러 | ❌ `tester`로 되돌림 |
| import·모듈 해석 실패 | ❌ `tester`로 되돌림 |
| 픽스처·설정 누락 | ❌ `tester`로 되돌림 |
| UI/E2E가 화면·서버 부재로 못 뜸 | ❌ red 아님. 선행 스캐폴드·green 단계로 되돌림 |

"빨갛다"와 "올바른 이유로 빨갛다"는 다르다. 후자만 구현 착수 근거다.

**6번 — 층을 합치지 않았나**

unit은 생략 불가다. UI가 없으면 테스트 계획의 구체적 사유로 UI 체인을 생략할 수 있다.
integration·e2e를 생략하려면 **사유와 승인**이 있어야 한다.
"이번엔 필요 없어서"는 사유가 아니다. "이 변경은 순수 함수만 건드리고 UI 경로가 없음"이
사유다.

**7번 — review가 테스트를 돌리고 있지 않나**

`review`는 판정만 한다. 증거가 없으면 판정하지 말고 6번으로 되돌린다.

### 1.4 실패했을 때 어디로 되돌리나

| 증상 | 되돌릴 곳 |
|---|---|
| 요구사항 슬롯 부족·수용 기준 모호 | `discussion` |
| 계약 드리프트·타입 불일치 | `spec` |
| 토큰 부재·대비 부족 | `design` |
| 테스트가 돌지 않음·red rejected | `tester` |
| 마크업·렌더 상태 | `implementation` |
| 데이터 페칭·상태 로직 | `state-data` |
| 커버리지 누락 | `tester` |
| 키보드·포커스·ARIA | `accessibility` (직접 고침) |

이 표의 단일 출처는 `profiles/frontend/profile.yaml`의 `routing`이다.

**재시도는 1회까지.** 같은 브리프로 두 번 실패하면 브리프를 보강하거나 상위로 올린다.
정책 거부(`policy-denied`)는 재시도 대상이 아니다 — 다시 해도 같은 이유로 거부된다.

## 2. 관리 — 하네스를 고칠 때

### 2.1 무엇을 고치면 무엇을 돌리나

| 고치고 싶은 것 | 어디를 | 그 다음 |
|---|---|---|
| 이관 조건 (앞 단계 증거 요구) | `workflows/gates/` + step의 `gate:` | `npm run check` |
| 역할이 하는 일 | `capabilities/<id>/agents/*.md` | `npm run check` |
| 도구·모델·권한 | `capabilities/<id>/capability.yaml` | `npm run check` |
| 선행조건·산출물·증거 | 같은 파일 | `npm run check` |
| 도메인 지식 (토큰·규칙) | `profiles/<id>/` | `npm run check` |
| 실행자 이름·단계 구성 | `profiles/<id>/profile.yaml` | `npm run check` |
| 작업 순서 | `workflows/*.yaml` | `npm run check` |
| 금지 규칙 | `policies/` | `npm run check` |
| 새 토큰 | `docs/vocabulary.md` **+** `vocabulary.json` | `npm run check` |
| 플랫폼 모델 이름 | `tooling/generators/platforms.json` | `npm run generate` |

**`.claude`·`.cursor`·`.codex`는 절대 직접 고치지 않는다.** 고쳐도 다음 생성 때
되돌아가고, CI가 병합을 막는다.

### 2.2 어디에 넣을지 판단하는 기준

새로 무언가를 추가할 때 **딱 하나만 물으면 된다.**

> 프론트엔드가 아닌 프로젝트에서도 이게 필요한가?

| 답 | 위치 |
|---|---|
| 예 | `capabilities/` |
| 아니오 | `profiles/frontend/` |

React 규칙 → 아니오 → 프로파일. 테스트 실행 → 예 → Capability.
디자인 토큰 → 아니오 → 프로파일. 계약 고정 → 예 → Capability.

판단이 애매하면 **프로파일에 넣는다.** 나중에 Capability로 올리는 건 쉽고,
Capability에서 도메인 지식을 빼내는 건 어렵다.

### 2.3 Capability 하나 추가하는 절차

```sh
mkdir -p capabilities/<id>/{agents,hooks}
```

1. `capability.yaml`을 쓴다. `id`는 디렉터리명과 같아야 한다.
2. `requires`/`produces`에 쓸 토큰이 `docs/vocabulary.md`에 있는지 본다.
   없으면 → 코어에 필요한가? 아니면 프로파일 네임스페이스(`<ns>:`)로.
3. **증거를 정한다.** 증거 없이 완료되는 Capability는 만들지 않는다.
   다음 단계가 상태가 아니라 증거로 넘어오기 때문이다.
4. `agents/*.md`에 본문을 쓴다. **frontmatter를 넣지 않는다** — 메타데이터는
   manifest가 소유하고, 남아 있으면 생성기가 오류로 잡는다.
5. `npm run check`.

중앙 registry도, 오케스트레이터도 고치지 않는다. 그게 이 구조의 목적이다.

### 2.4 검증기가 막아주는 것 / 안 막아주는 것

**막아준다** (틀리면 즉시 실패)

- 어휘 오타, 없는 파일 참조, 권한 초과, 프로파일의 권한 확대
- 테스트 층 합치기, Git 작업 자동화, 파괴적 작업 자동 진행
- 오케스트레이터에 도메인 지식 유입, 미러 드리프트

**안 막아준다** (사람이 봐야 함)

- 역할 본문이 실제로 말이 되는지
- 워크플로 순서가 이 조직에 맞는지
- 증거를 정말 남겼는지 (기록 주체가 없다)
- 훅이 요구하는 검사를 실제로 했는지

즉 **"구조가 일관적인가"는 자동, "내용이 옳은가"는 수동**이다.

### 2.5 정기 점검

```sh
npm run check          # 선언 + 드리프트
git status             # 미러가 손으로 고쳐지지 않았는지
```

주기적으로 볼 것:

- `policies/README.md`의 ⏳ 항목이 아직도 강제되지 않는가 → ADR-0002 조건 재검토
- `docs/vocabulary.md`에 아무도 안 쓰는 토큰이 쌓이지 않았는가
- 에이전트 `description`이 길어지지 않았는가 (세션마다 로드되는 유일한 부분)
- `profiles/`가 하나뿐인가 → 하나면 "도메인 무관"은 아직 검증되지 않은 주장이다

## 3. 자주 하는 실수

| 실수 | 왜 문제인가 |
|---|---|
| 미러를 직접 고침 | 다음 생성에 사라짐. CI가 막음 |
| 본문 md에 frontmatter를 넣음 | manifest와 갈라짐. 생성기가 오류 |
| Capability에 프레임워크 이름을 씀 | 프로파일 교체해도 도메인이 따라옴 |
| 증거 없이 다음 단계로 감 | 무엇이 왜 통과했는지 사후에 알 수 없음 |
| 컴파일 에러를 red로 침 | 초록이 됐을 때 요구사항 만족인지 에러 소멸인지 구분 불가 |
| 커밋 후 자동으로 푸시 | 되돌리기 어려운 작업을 의도하지 않은 시점에 실행 |
| 어휘 파일을 한쪽만 고침 | 사람이 읽는 것과 기계가 읽는 것이 갈라짐 |
