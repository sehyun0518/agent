# orchestrator

작업 Capability를 조립하는 **조정자**. Capability가 아니다.

## 왜 Capability가 아닌가

`requires`/`produces`로 표현되는 작업 단계가 아니라 횡단 관심사이기 때문이다.
오케스트레이터를 Capability로 두면 자기 자신을 registry에 등록해야 해서 순환이 생긴다.
(ADR-0001 D7)

## 무엇을 모르는가

`orchestrator.md`에는 **특정 Capability나 명명 에이전트가 등장하지 않는다.**
검증기가 이걸 검사한다.

| 아는 것 | 모르는 것 |
|---|---|
| 작업의 구조 — 무엇을·어떤 순서로·누구에게 | 그 "누구"의 실제 이름 |
| 완결성 게이트와 스펙 포맷 (`requirements-spec` 스킬) | 도메인 지식 (토큰·프레임워크·컨벤션) |
| 실패 분류와 에스컬레이션 경로 | 어떤 명령으로 무엇을 돌리는지 |

순서는 워크플로가, 실행자 이름은 활성 프로파일의 `roster`가, 도메인 단계의 삽입 지점은
`workflowExtensions`가, 지적의 소유자는 `routing`이 정한다. 프로파일을 교체하면 같은
오케스트레이터가 다른 도메인에서 돈다.

## 이관 기록

구 `agents/orchestration.md`의 §0~8이 이 문서다. §9 "프론트엔드 인스턴스화"는
`profiles/frontend/profile.yaml`로 옮겨졌다.

분리 전에는 역할이 하나 늘 때마다 §9의 로스터·DAG·라우팅 세 곳을 고쳐야 했다.
이제 Capability를 추가해도 이 문서는 바뀌지 않는다.

## 아직 코드가 아니다

ADR-0001 D2에 따라 이 패키지는 선언(프롬프트 본체)만 담는다. 실행 코드로의 승격은
manifest 계약이 안정된 뒤 ADR-0002에서 정한다. 승격 시 이 문서는 런타임의 명세가 된다.
