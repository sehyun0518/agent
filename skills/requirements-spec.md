# Requirements Spec — 요구사항 스펙 계약

## 목적

이 스킬은 프론트엔드 파이프라인의 모든 레이어가 공유하는 **단일 출처(source of truth)** 다. 스키마와 스펙 포맷을 각 에이전트 프롬프트에 중복 정의하면 레이어마다 정의가 갈라져(drift) 같은 스펙을 서로 다르게 해석하게 된다. 그래서 정의는 여기 한 곳에만 두고, 각 레이어는 이 스킬을 참조한다.

이 계약은 특정 에이전트 몇 개가 "소유"하는 게 아니라, **레이어 경계를 넘을 때마다 검사되는 불변식(invariant)** 이다. 산출물이 한 레이어에서 다음 레이어로 이동하는 모든 지점(handoff)에서 이 계약에 부합하는지 확인한다. 경계마다 하는 동작은 다르지만(채우기 / 읽기·게이트 / 검증), 기준은 언제나 이 스킬 하나다. 그래서 "소비자 N명"으로 외우면 안 된다 — 목록은 닫힌 집합처럼 굳어서 레이어를 추가·재배치하면 깨진다. **"경계마다 검사"** 로 기억한다.

경계 예시:

- **논의 → 오케스트레이터**: 스펙을 산출하고, 완결성 게이트로 검사.
- **오케스트레이터 → 실행**: 스펙 슬라이스를 브리프에 담아 넘김. 격리된 실행자에게는 이 계약 조각이 세계 전부.
- **실행 → 피드백**: `acceptance_criteria`가 그대로 검증 게이트가 됨.
- **되돌림(loop-back)**: 어느 경계든 미달이면, 같은 계약으로 부족한 슬롯을 지정해 이전 레이어로 반환.

레이어를 추가하거나 순서를 바꿔도 규칙은 그대로다: **경계가 생기는 곳에 이 계약 검사를 둔다.**

## 요구사항 스키마

각 슬롯은 아래 `채워짐 판정 기준`을 통과해야 "채워진" 것으로 본다. 통과하지 못하면 빈 칸으로 취급한다. 판정 기준을 둔 이유는, 슬롯에 글자가 들어있다고 채워진 게 아니라 *실행 가능한 수준의 구체성*이 있어야 채워진 것이기 때문이다.

### 필수 슬롯 (하나라도 비면 미완결)

| 슬롯 | 설명 | 채워짐 판정 기준 |
|---|---|---|
| `goal` | 무엇을, 왜 만드는가 (기능이 아니라 목적/job-to-be-done) | "무슨 화면"이 아니라 "사용자가 무엇을 달성하나"가 한 문장으로 적힘 |
| `target` | 타깃 유저 · 디바이스 · 브라우저 지원 범위 | 디바이스(모바일/데스크톱/둘 다)와 지원 브라우저 하한이 특정됨 |
| `design_ref` | 디자인 시스템 / 토큰 / 컴포넌트 컨벤션은 `AGENT.md`에서 링크하는 `DESIGN.md`를 따른다. 이 슬롯은 그 표준을 **따른다는 사실 + 이번 작업의 의도적 벗어남(deviation)만** 기록한다. | 기본값 "DESIGN.md 표준 따름"으로 충족됨. 벗어나는 부분이 있으면 그것이 명시됨 (없으면 그대로 통과) |
| `scope_in` | 이번 작업에 포함되는 것 | 만들 화면/컴포넌트/상호작용이 열거됨 |
| `scope_out` | 명시적으로 제외하는 것 | 최소 1개 이상 "이번엔 안 함" 항목이 적힘 (없으면 "없음"으로 명시 확인) |
| `acceptance_criteria` | "완료"의 정의 (→ 피드백 레이어의 검증 타깃) | 객관적으로 통과/실패 판정 가능한 기준이 2개 이상 |

### 권장 슬롯 (비어도 진행 가능하지만 확인 권장)

| 슬롯 | 설명 |
|---|---|
| `constraints` | 성능 예산, 접근성 요구(WCAG 등), 기술 스택 제약 |
| `visual_reference` | 레퍼런스 이미지 / "X처럼, 단 Y는 다르게" / 와이어프레임 |
| `priority` | 속도 vs 완성도 등 트레이드오프 우선순위 |
| `data_state` | 상태·데이터 연동 필요 여부, API 유무 |

프론트엔드 특성상 `visual_reference`는 텍스트로 전달 손실이 가장 큰 슬롯이다. 비어 있으면 본 작업 전에 저해상도 와이어프레임으로라도 한 번 맞추도록 유도한다. 텍스트만으로 시각 의도를 합의했다고 가정하면 거의 항상 재작업이 난다.

### 디자인은 슬롯이 아니라 참조다

디자인 시스템·토큰·컴포넌트 컨벤션은 **느리게 변하는 프로젝트 상수(지식 레이어)** 다. 작업마다 사용자에게 다시 물어 채울 요구사항이 아니라, `AGENT.md`에서 링크하는 **`DESIGN.md`** 에 한 번 박아두고 모든 작업이 참조한다. 그래서 `design_ref` 슬롯은 디자인 내용을 담지 않고, "DESIGN.md를 따른다"는 사실과 이번 작업의 *의도적 벗어남*만 기록한다.

이건 "발화 외 정보로 슬롯을 채우지 않는다"는 규칙과 충돌하지 않는다. `DESIGN.md`는 채우는 쪽이 런타임에 파일로 *읽어오는* 외부 자료가 아니라, `AGENT.md`를 통해 이미 컨텍스트에 상시 로드된 프로젝트 기반이기 때문이다. 즉 디자인 표준은 "조사해서 알아내는 것"이 아니라 "처음부터 깔려 있는 것"이다.

## 완결성 판정 (Definition of Done)

스펙을 "완결"로 보고 다음 레이어로 넘기려면 아래를 **전부** 만족해야 한다. 이 정의는 논의 에이전트의 산출 게이트와 오케스트레이터의 인테이크 게이트에서 **동일하게** 쓰인다 — 그래서 사용자가 요구사항을 직접 줬든 논의 에이전트를 거쳤든 같은 잣대로 검사된다.

- [ ] 6개 필수 슬롯이 모두 "채워짐" 판정을 통과
- [ ] `acceptance_criteria`가 객관적으로 검증 가능한 기준 2개 이상
- [ ] `[추론]` 태그가 붙은 슬롯이 모두 사용자 확인을 받았거나, 미확인 항목이 스펙 "비고"에 명시됨
- [ ] 미해결/모순 항목이 0개

미달이면 진행하지 말고, **어떤 슬롯이 왜 부족한지 목록과 함께** 논의 레이어로 되돌린다.

## 슬롯 채우기 규칙 (채우는 쪽)

- 슬롯은 **(a) 사용자가 발화에서 명시한 것** 또는 **(b) 발화에서 추론하고 `[추론]` 태그를 단 것**으로만 채운다.
- 외부 파일·레포·일반 지식으로 빈 칸을 메우지 않는다. 발화 밖 정보로 채우는 것은 금지.
- 둘 다 아니면 슬롯을 비워두고 질문으로 돌린다. 절대 그럴듯하게 지어내지 않는다(환각 금지).
- `[추론]` 슬롯은 사용자 확인을 받기 전까지 태그를 유지한다.

## 스펙 / 계약 문서 포맷 (읽는 쪽·쓰는 쪽 공통)

완결 시 **반드시 아래 템플릿 그대로** 산출한다. 이 포맷이 고정돼 있어야 오케스트레이터가 슬롯을 안정적으로 파싱하고, 피드백 레이어가 수용 기준을 정확히 집어낼 수 있다.

```markdown
# 작업 스펙: <짧은 제목>

## 목적 (goal)
<job-to-be-done 한 문장>

## 타깃 (target)
- 디바이스: <...>
- 브라우저 하한: <...>

## 디자인 (design_ref)
DESIGN.md 표준 따름. 벗어남: <의도적 deviation만, 없으면 "없음">

## 범위
- 포함(scope_in): <...>
- 제외(scope_out): <...>

## 수용 기준 (acceptance_criteria)  ← 피드백 레이어 검증 타깃
1. <통과/실패 판정 가능한 기준>
2. <...>

## 제약 (constraints)
<성능 예산 / 접근성 / 스택 제약, 없으면 "없음">

## 시각 레퍼런스 (visual_reference)
<레퍼런스/와이어프레임, 없으면 "본 작업 전 와이어프레임 확인 필요">

## 우선순위 / 데이터 (선택)
<priority, data_state>

## 비고
- [추론] 표시 항목: <사용자 미확인 추론이 남아있다면 여기에>
```

## 읽기·게이트 규칙 (읽는 쪽)

- 들어온 스펙을 위 "완결성 판정"에 대고 검사한다. 입력이 사용자 직접 요구사항이어도 "완결됐겠지"라고 가정하지 않는다.
- `acceptance_criteria`의 각 항목은 그대로 실행 단위의 피드백 게이트로 분배된다. 그래서 이 항목들이 객관 판정 가능해야 한다 — 모호한 기준은 게이트로 쓸 수 없으니, 발견 즉시 논의 레이어로 되돌려 구체화시킨다.
- 스펙에 없는 정보는 추측해서 채우지 않는다. 부족하면 되돌린다.
