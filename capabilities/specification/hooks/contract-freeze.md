# Hook — 계약 고정

- 이벤트: `after-capability`
- blocking: 예. 통과하지 못하면 `specification.completed`를 낼 수 없다.
- 산출 증거: `changed-files` · `contract-diff`

## 왜 필요한가

병렬 실행이 서로 깨지지 않는 이유는 대화가 아니라 계약이다. 계약이 "고정 가능한
파일"로 존재하지 않으면 하류가 기댈 것이 없고, 각자 추측하다 어긋난다.

## 검사

1. 계약이 **파일로** 존재하는가 — 대화 속 서술이 아니라 하류가 읽을 수 있는 산출물인가
2. 다음이 빠짐없이 고정됐는가
   - 타입과 컴포넌트 props 인터페이스
   - API 요청/응답 스키마
   - 데이터 접근 인터페이스(훅 시그니처) — 실제 훅 없이도 하류가 코딩할 수 있어야 한다
   - test-id 규약 — DOM 없이도 테스트를 작성할 수 있어야 한다
3. 이전 고정본이 있으면 차이가 `contract-diff`로 기록됐는가
4. 계약에 모순이나 미정 항목이 남아 있지 않은가

## 증거 기록

```yaml
kind: contract-diff
status: recorded | violated
summary: "신규 인터페이스 4, 변경 1, 제거 0"
artifact: <경로>
producedBy: specification
```

`violated`는 이미 고정된 계약이 재고정 절차 없이 바뀐 경우다. 이때는
`contract-violation`으로 분류한다.

## 하류에 대한 약속

이 훅을 통과한 시점부터 계약은 고정이다. 하류는 계약이 부족하거나 모순되면
**추측하지 않고** 이 Capability로 되돌린다.

### 되돌린다는 것이 무엇인가

**흐름을 되감는 실행 주체는 없다** (ADR-0002). 되돌림은 사람 또는 메인 에이전트가
`specification`을 다시 부르고 그 뒤부터 다시 진행하는 것이다. 재개 규칙은 하나다.

> 재고정된 산출에 **의존하는 하류 단계의 증거는 무효**다. 지우지 않고 남기되, 다시
> 실행한 증거가 그 위에 쌓인다. 무엇이 무효인지는 `contract-diff`가 무엇을 바꿨는지가
> 정한다.

의존하지 않는 계층까지 다시 돌리지 않는다. 계약의 어느 부분이 바뀌었는지 모르면
전부 다시 도는 것이 안전하지만, 그건 `contract-diff`를 안 남겼다는 뜻이다.

### 되돌리지 않기로 했다면

되돌림이 늘 옳은 것은 아니다. 이탈이 작고 되돌림이 과할 때가 있다. 그때는 **선택을
증거로 남기고 승인을 받는다.**

```yaml
kind: contract-deviation
status: recorded
summary: "계약 §5.2가 암시하는 렌더 대상에 test-id가 없어 <대안>을 택함"
artifact: <경로>
producedBy: implementation#ui
```

**기록만으로는 진행할 수 없다.** `approval-record: granted`가 함께 있어야 한다.
계약을 따르지 않기로 한 선택은 우회이고, 승인은 우회에 붙는다.

승인 없이 진행하면 그 위에 쌓이는 계층들이 전부 검증되지 않은 가정 위에 서고,
판정 단계가 그것을 알아차릴 때는 이미 되돌리기에 비싸다. FE 실행에서 실제로
그렇게 됐다 — 세 계층이 쌓인 뒤에야 이탈이 드러났다.

## 범위 밖

계약을 커밋하는 것은 이 Capability의 일이 아니다. 커밋은 `git-operations#commit`의
독립 호출이며, 어떤 Capability도 이를 자동 호출하지 않는다.
